# Замер BatchSize=1 (строгий последовательный режим) — 2026-11-08

Цель: живым замером проверить утверждение «производительность падает с тысяч msg/s до сотен» (README «Гарантия порядка» — режим батча из одного сообщения, документированный режим строгой последовательной доставки). До этого замера BatchSize=1 не было — прогоняли только 500/1000/2000 (`loadtest-text-binary-batchsize.md`).

## Условия

- Стенд целиком на одном хосте (Docker Desktop, macOS arm64) — абсолютные цифры специфичны для среды.
- `cdc-outbox-1` с временным `docker-compose.override.yml` (env `CDCOUTBOX__PROCESSOR__BATCHSIZE=1`; методика — как эксперимент BatchSize 1000/2000 из `loadtest-text-binary-batchsize.md`); `cdc-outbox-2` (standby) остановлен на время замера, чтобы не перехватил лидерство при пересоздании контейнера.
- Остальное — дефолты: текстовое декодирование, `QueueCapacity=2048`, `CheckpointIntervalSeconds=5`, продюсер `BatchNumMessages=10000`/`LingerMs=5`, транзакционный продюсер — батч из одного сообщения = одна транзакция (Begin → produce → delivery → commit).
- Нагрузка: Writer 3 000 × 256 Б без rate limit — запись завершается за секунды, далее чистый дренаж бэклога: меряется потолок конфигурации.
- Замер: `outbox_processor_sent_messages_total` cdc-outbox-1 (:18084) сэмплами каждые 3 с.

## Результат

- **Пропускная способность ≈ 40 msg/s** (сэмплы 34–47/s по 3-с окнам), цикл ≈ 25 мс на сообщение.
- Против 25 274 msg/s чистого дренажа при батче 500 — падение в ~600 раз. Утверждение «до сотен» фактически неверно для этого стенда: **десятки**, не сотни.
- Экстраполяция измеренной кривой 500/1000/2000 (линейная аппроксимация цикла: интерцепс ≈ 15 мс) предсказывала ~66 msg/s — реальность хуже: при батче 1 в полную цену каждого сообщения выходят и linger (5 мс), и commit-маркеры транзакции.
- Корректность в режиме подтверждена: вердикт валидатора по прогону — written=3000, missing=0, extra=0, ambiguous=0.

## Почему так мало: декомпозиция цикла (дополнительный замер LingerMs=0)

Ожидание «несколько сотен msg/s» предполагает цикл ≤5–10 мс на сообщение. Повторный замер (2 000 × 256 Б, `BatchSize=1` + `LingerMs=0`, та же методика) раскладывает измеренные ~22–25 мс на составляющие:

| Составляющая цикла | Время | Откуда |
|---|---|---|
| produce → ACK одного сообщения (`acks=all`, 3 брокера) | **~20.6 мс** (среднее) | гистограмма `outbox_processor_publish_latency_seconds`: sum 41.17 с / 2000 |
| commit транзакции (EndTxn + маркеры) + служебное | ~1.5 мс | цикл 22.0 мс − путь публикации 20.6 мс |
| linger (`LingerMs=5`) | ~3 мс | цикл 25.1 мс при linger 5 против 22.0 мс при linger 0 |

Итог без linger: ~45 msg/s (цикл 22.0 мс), с linger: ~40 msg/s (цикл 25.1 мс).

Доминирует не механика сервиса, а **round-trip одного сообщения до подтверждения `acks=all` на этом стенде**: репликация ISR через виртуализированную сеть Docker Desktop (macOS/arm64, брокеры в VM) даёт ~20 мс на одиночный produce. Распределение бимодальное: 23% сообщений ≤5 мс, основная масса 10–25 мс, хвост до 50–100 мс.

Тот же round-trip ограничивает и дефолтный режим — там он амортизируется батчем: цикл транзакции при батче 500 ≈ 19.8 мс **на весь батч** (≈50 коммитов/с × 500 = 25 274 msg/s). При батче 1 амортизации нет — каждое сообщение платит round-trip целиком.

Оценка «до сотен msg/s» предполагала round-trip ~1–3 мс (ближняя сеть/голое железо): цикл = RTT + commit ≈ 3–5 мс → 200–300 msg/s. На стенде с RTT ~20 мс последовательный режим упирается в ~40–45 msg/s — ограничение среды, не дефект конвейера.

## После замера

Стенд возвращён к дефолту: override-файл удалён, cdc-outbox-1 пересоздан с `BatchSize=500` и активен, cdc-outbox-2 запущен в standby (пара Active-Passive поднята).
