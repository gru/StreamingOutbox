# Тестирование отказоустойчивости CDC-конвейера — 2026-11-07

Цель: проверить поведение outbox-сервиса при отказах каждого компонента стенда. Подход — зафиксированный в `docs/stand.md` («Отказы и восстановление»: инъекции `stand.sh fail/restore/switchover` под нагрузкой, вердикт валидатора после каждого) и приёмочный харнесс `scripts/test/integration-delivery.sh`. Критерий pass — как в харнессе: `missing=0 && unexpected=0`; дубликаты не фейлят (контракт at-least-once: дедупликация — ответственность потребителя).

Две фазы: **A** — приёмочный харнесс (рестарт активного, kill лидера PG, kill брокера, полный outage Kafka, failover пары Active-Passive), **B** — сценарии, не покрытые харнессом (kill реплики PG, полный отказ PG, kill HAProxy, kill standby, полный отказ доставки, graceful switchover). Каждый сценарий — под нагрузкой Writer (инъекция в середине прогона 600–1000 сообщений @30–50/с), восстановление `restore`, вердикт валидатора.

## Условия

- Стенд целиком на одном хосте (Docker Desktop, macOS arm64).
- Пара Active-Passive поднята (профиль `redundancy`): старт — активен cdc-outbox-1, cdc-outbox-2 standby; `stand.sh check` 62/62.
- Конвейер в дефолте: `BatchSize=500`, `QueueCapacity=2048`, `CheckpointIntervalSeconds=5`, транзакционный продюсер (checkpoint в транзакции батча).
- Каждая инъекция — `docker compose kill` («ручная остановка», рестарт-политика не применяется), возврат только явным `restore` (у cdc-outbox рестарт-политики нет по решению владельца).
- Топологии PG за сессию: timeline 12 → 13 (T4a, лидер pg2→pg1) → 14 (B2 pg-all, лидер снова pg1) → 15 (B6 switchover, лидер pg1→pg2).

## Фаза A: приёмочный харнесс — 97 PASS / 1 FAIL

Полный лог — `faulttest-phasea-harness.log`. Провален один ассерт (не вердикт доставки):

**T4c `retained WAL не растёт (267536 → 148528)`** — артефакт измерения, не дефект продукта. Ассерт сравнивает `pg_slot_wal_retained_bytes` до прогона и во время outage, неявно предполагая дренированный базлайн. Фактически RET0=267 КБ — несброшенный хвост T4b: в простое checkpoint'ы не пишутся (heartbeat отсутствует сознательно), `restart_lsn` заморожен на последнем подтверждении. За 8 с прогона до kill (Kafka жив) позиция подтвердилась дальше устаревшего базлайна; неподтверждаемый хвост окна outage (148 КБ) оказался меньше. Семантика, которую проверяет ассерт, выполнилась — и доказана независимо в B5 от чистого базлайна: retained вырос ровно на WAL окна outage (+209 КБ) и был отпущен после дренажа (680→22 КБ).

Рекомендация по харнессу (за владельцем): перед RET0 дождаться дренированного слота (`outbox_checkpoint_lag_bytes=0` + пауза) или сравнивать RET1 с дренированным минимумом, а не с RET0.

## Фаза B: детали по сценариям

Лог — `faulttest-phaseb-scenarios.log`. Счётчики CDC — до/после каждой инъекции (`outbox_slot_reconnects_total`, `outbox_processor_errors_total`, `outbox_failovers_total`, `outbox_processor_is_active`).

- **B1 (реплика)**: прогон завершился в плановые ~20 с (инъекция на 10-й секунде) — walsender на лидере не затронут, reconnects 0, is_active без изменений. Восстановление pg2 — без смены лидера, кластер 3/1.
- **B2 (pg-all)**: окно отказа ~30 с (kill 3 ноды + 20 с наблюдение + restore 72 с от инъекции). Writer: /ready 503, прогон на ретраях, после restore дописал хвост — 600/600, failed=0. CDC: лидерство удержано (восстановимые ошибки — повторы с backoff, хост не останавливается), reconnects 2, errors_total 2. Дубли 400: при темпе 30/с батч-транзакция (BatchSize=500) не успела закоммититься к kill — записи попали в Kafka, подтверждения LSN не было → пере-доставка после переподключения от `confirmed_flush`. Postgres-exporter залип после выборов — рестартнут харнессом автоматически (документированное поведение).
- **B3 (haproxy)**: разрыв пути записи до PG у Writer и CDC. CDC: 2 переподключения (backoff), после restore всё дописанное доставлено, dup=0. Writer (тестовый генератор): прогон failed — в резервировании id вылетел голый `SocketException: Name or service not known` (остановленный контейнер haproxy перестаёт резолвиться в Docker DNS), классификатор транзиентности Writer'а признаёт только SocketException **внутри** NpgsqlException → фатал, 100 сообщений не дописано. Доставка объекта теста не затронута: пул соединений CDC и его классификатор сетевых ошибок отработали.
- **B4 (standby)**: инъекция без последствий — прогон по расписанию, dup=0; лидер (failovers=1, reconnects=5) не заметил; возврат cdc-outbox-2 — standby (1/0).
- **B5 (outbox-all)**: обе инъекции под нагрузкой 1000@50/с, kill на 6-й секунде (~250 записано до, ~750 в outage). Writer завершился через 13 с после инъекции — запись от CDC не зависит. Слот: active=f, wal_status=reserved, retained 471 400 → 680 128 байт (+209 КБ ≈ WAL ~1000 транзакций окна). Restore (41 с от инъекции): лидерство взял cdc-outbox-1 (первое избрание в новом процессе, failovers=1), бэклог дренирован к моменту опроса. Дубли 100 — та же механика окна. После дренажа retained 22 КБ, confirmed_flush == restart_lsn — WAL отпущен.
- **B6 (switchover)**: зависание graceful switchover при живом консюмере слота воспроизведено (документированная грабля стенда, унаследованная): REST-запрос 503 «Switchover status unknown», pg1 завис в состоянии `leader/stopping` на ~10 минут — demote ждёт закрытия walsender слота; pg2 не промоутится, запись стоит. Лечение из документации подтверждено: рестарт активного экземпляра cdc-outbox → switchover завершился за ~3 с (pg2 лидер, timeline 15), далее `apply-bootstrap.sh`. Побочно корректно отработала пара: в момент рестарта лидера лидерство мгновенно принял cdc-outbox-2 (graceful stop = LeaveGroup), cdc-outbox-1 вернулся standby. Доставка: 400/400 записанного, dup=0. Writer: во время зависшего demote прогон стоял на ретраях, на промоушене pg2 поймал `25006 read-only` (мгновение, пока HAProxy ещё вёл запись на уже demoted pg1) — класс нет в транзиентных списках Writer'а → фатал, 200 не дописано.

## Находки (всё — вне продукта; конвейер во всех сценариях pass)

1. **Ассерт T4c харнесса чувствителен к базлайну** — сравнивать retained WAL с дренированным состоянием (см. выше). Продукт: поведение корректно (доказано в B5).
2. **Writer: голый SocketException (DNS) при резервировании id классифицируется фатальным** — прогресс B3. Классификатор (`OutboxWriter.IsTransient`) распознаёт SocketException только обёрнутым в NpgsqlException. Влияет только на тестовый контур: прогон падает, недописанное не попадает в outbox (потерь нет — вердикт по записанному pass). Возможный фикс (за владельцем): считать транзиентным также голый `SocketException` в резервировании id.
3. **Writer: 25006 (read-only) не в списке транзиентных SQLSTATE** — прогресс B6; тот же эффект (фатал прогона на окне failover). Примечательно: у CDC-сервиса 25006 транзиентен по контракту (`outbox-table.md`), у Writer'а список уже — 08xxx/53300/57P0x/40001/40P01/55P03/54000. Возможный фикс — дополнить список (за владельцем).
4. **Switchover-вис** — известная грабля стенда (фиксирована в docs/stand.md), воспроизведена и благополучно вылечена штатным способом. Кандидат на отдельное решение в будущем (например, scripted switchover, останавливающий сначала активный cdc-экземпляр).
