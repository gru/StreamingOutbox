# Исходные требования и отступления

Требования, с которых начиналась разработка (архитектура и гарантии доставки, стек и схема, исходный список метрик ТЗ), зафиксированы ниже; ранее они хранились в docs/ (после сокращения документации архитектура доставки — README.md, версии и контракты окружения — раздел «Версии и контракты» AGENTS.md). По ходу реализации часть положений уточнена или изменена — каждое изменение сначала фиксировалось в документации решением владельца, затем в коде. Ниже — исходный список и отступления с причинами.

## Исходные требования

1. Чтение outbox — только через слот логической репликации (`pgoutput`), SELECT-polling запрещён; только INSERT outbox-таблицы из отдельной publication; границы транзакций источника соблюдаются.
2. Слот создаёт сам сервис при первом запуске, идемпотентно (не миграция); существующий переиспользуется; автопересоздание утраченного слота при живом checkpoint запрещено.
3. Конвейер строго `WAL Read → Kafka Send → Kafka ACK → Durable Checkpoint → LSN Flush`: ни checkpoint, ни подтверждение LSN не опережают подтверждённую доставку; продвижение позиции монотонно, на границах полностью обработанных транзакций.
4. Доставка at-least-once; exactly-once между PostgreSQL и Kafka не обеспечивается; дедупликация — Inbox потребителя.
5. Checkpoint Store — отдельный Kafka-топик с log compaction: запись только после Kafka ACK, сохранена = подтверждение записи; при старте — загрузка последнего значения и согласование со слотом.
6. Recovery Mode — ручной флаг аварийного восстановления: старт от текущей позиции, пересоздание отсутствующего слота допустимо, новый checkpoint до начала чтения; режим допускает осознанный пропуск окна.
7. Backpressure — ограниченная очередь чтение→доставка; размеры пачек, очередей и in-flight конфигурируемы; память не растёт неограниченно.
8. Переподключения с backoff; терминальные потери (слот утрачен, WAL недоступен) — явная ошибка, не тихий пропуск; graceful stop сохраняет подтверждённый прогресс.
9. Резервирование Active-Passive: consumer group на служебном топике, transactional producer с постоянным `transactional.id` (fencing), checkpoint при восстановлении — последнее значение по ключу, не group offset; старый лидер не переинициализирует продюсер.
10. Продюсер: `acks=all`, идемпотентность, батчинг и таймауты — конфигурируются; событие опубликовано = получен ACK, не «отправлено в буфер».
11. Порядок публикации соответствует порядку WAL; checkpoint не обгоняет неподтверждённые события.
12. Контроль простоя потока и порядок обновления PostgreSQL (pg_upgrade ≥ 17 переносит слоты, dump/restore — нет; после миграции — recovery-согласование).
13. Метрики — исходный список ТЗ (15, включая `outbox_saved_messages_total`), у процессорных — label `partition`.
14. Стек: .NET 8, PostgreSQL 17, Npgsql, Confluent.Kafka; Kafka-клиент унаследован от исследовательского стенда (KafkaFlow).

## Отступления и их причины

| Что изменилось                                                                                                                                                                            | Почему                                                                                                                                                                                                                                                                                                                                                                                                  |
|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **KafkaFlow исключён, клиент — только Confluent.Kafka напрямую** (2026-10-22)                                                                                                             | KafkaFlow не даёт доступа к Kafka-транзакциям ни в одной линии (feature request открыт без реакции; проверено рефлексией сборки) — а транзакционный продюсер нужен для fencing лидера и атомарности «батч + checkpoint». В валидаторе KafkaFlow удалён отдельно (2026-10-27): дефект связки с Confluent 2.3.0 — консюмер назначал партиции и не доставлял записи (воспроизведено минимальным пробником) |
| **Drain-режим исключён — вместо него idle-предупреждение**                                                                                                                                | Сервис рассчитан на постоянно пишущиеся outbox; при отсутствии событий он продолжает держать слот и доставлять всё, что появляется. Heartbeat-механизм сознательно отсутствует (2026-11-02): слот без событий не подтверждается и WAL копится — именно об этом предупреждает WARN                                                                                                                       |
| **`acks` — не настройка, зашито `all`** (2026-11-04)                                                                                                                                      | Единственное значение, допустимое для транзакционного продюсера; настройка создавала иллюзию выбора                                                                                                                                                                                                                                                                                                     |
| **`outbox_saved_messages_total` не реализуется; `partitioning_…` не переносится; label `partition` у всех метрик заменён на `slot`** (2026-11-04)                                         | Метрика сохранения — событие пишущей стороны, сервис в outbox не пишет; `partitioning_…` — `[Obsolete]` исходника. Единый `slot` нужен мульти-слотовой модели (общий мониторинг и общий checkpoint-топик): без label наблюдения разных слотов смешивались бы                                                                                                                                            |
| **Опережение checkpoint'ом `confirmed_flush` при живом слоте — не терминальная ошибка** (2026-11-04; было терминальным)                                                                   | Данные до checkpoint уже в Kafka — доказательством служит сам закоммиченный checkpoint (инвариант «checkpoint в одной транзакции с доставкой»). Прежнее поведение давало ложные аварии при доказанно доставленных данных (гналось приёмкой); теперь — продолжение с позиции слота с WARN                                                                                                                |
| **Recovery Mode: ключ одним словом; пересоздание только отсутствующего слота; no-op при согласованном состоянии** (2026-11-02)                                                            | `RECOVERY_MODE` молча терялся binder'ом конфигурации (одинарное подчёркивание — не разделитель) — ключ стал `RECOVERYMODE`. Автодроп существующего слота запрещён: он может быть чужим. Забытый флаг безопасен — при согласованном состоянии старт проходит без изменений                                                                                                                               |
| **Слот без `failover` принимается с WARN; publication с лишними операциями — тоже**                                                                                                       | `failover` — инфраструктурное решение о переживании promotion, чтению флаг не требуется; для доставки значимы только INSERT, лишние записи декодируются, но не обрабатываются                                                                                                                                                                                                                           |
| **Исчезновение слота (42704) — транзиентная ошибка, сервис не падает**                                                                                                                    | У среды выполнения может не быть рестарт-политики; слот может появиться после смены primary (окно досинхронизации failover-копии) или вмешательства оператора; системное решение — Recovery Mode на следующем рестарте                                                                                                                                                                                  |
| **Восстановимые ошибки запуска лидерства не останавливают хост** (2026-11-05)                                                                                                             | Приёмка поймала транзиентный обрыв чтения PG в момент стартовых проверок — хост остановился и лежал без рестарт-политики, хотя повтор через секунды прошёл бы. Теперь — повторы с backoff и свежим DI-скоупом с удержанием лидерства; терминальные нарушения выведены в `StartupCheckException`                                                                                                         |
| **Многопартиционность общего checkpoint-топика отклонена: партиция одна (заморожено), слоты разводятся контрольными группами `cdc-outbox-<slot>`; настройка группы удалена** (2026-11-06) | Общая группа на все пары при «один экземпляр = один слот» неработоспособна (assignor не знает слотов); модель «любое назначение партиции = лидерство» верна только при единственной партиции; выигрыш многопартиционности при объёме checkpoint-записей маргинален, а число партиций keyed-топика фактически заморожено. Явная настройка группы была риском молчаливой коллизии двух пар                |
| **Продюсер — сервис периода лидерства, на каждый период свежий экземпляр** (2026-11-04, дефект приёмки)                                                                                   | Повторный `InitTransactions` на уже инициализированном продюсере невалиден (состояние Ready) — приводил к терминальной остановке при повторном получении лидерства тем же процессом                                                                                                                                                                                                                     |
| **Транспортный интерфейс публикации не вводится**                                                                                                                                         | Абстракция стесняет реализацию: батчинг, delivery-репорты и транзакционный продюсер checkpoint'ов требуют прямого доступа к клиенту                                                                                                                                                                                                                                                                     |
| **`/ready` без чека процессора доставки**                                                                                                                                                 | Готовность ≠ лидерство: standby не держит цикл доставки, но экземпляр здоров; активность отслеживает метрика `outbox_processor_is_active`                                                                                                                                                                                                                                                               |
| **Тесты: ассерты Shouldly; интеграционные — compose-мини-стенд, Testcontainers отклонён**                                                                                                 | Shouldly — решение владельца для всех тестовых проектов. Testcontainers тянет новые пакеты, точку входа ryuk и доступ к docker.sock из контейнера тестов; compose-стенд детерминирован и обозрим                                                                                                                                                                                                        |

## Что осталось неизменным

Главный инвариант пережил все правки без изменений: **ни checkpoint, ни подтверждение LSN слота никогда не опережают подтверждённую Kafka-доставку** — конвейер `чтение → отправка → ACK → durable checkpoint → подтверждение`, at-least-once, дедупликация на потребителе, Active-Passive с fencing через Kafka-транзакции.
