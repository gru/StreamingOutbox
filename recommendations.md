# recommendations.md — рекомендации по реализации CDC-сервиса

Рекомендации основаны на инженерных подходах Debezium (Debezium Connector / Debezium Server Kafka Sink) и ориентированы на собственный CDC-сервис для высоконагруженных outbox-таблиц. Вместе с `dependencies.md` образуют проектную основу реализации: `dependencies.md` — стек и схема, этот файл — архитектура и гарантии доставки.

---

# Часть I. CDC-сервис на PostgreSQL

### 1. Чтение через Logical Replication Protocol

- Использовать стандартный PostgreSQL Logical Replication Protocol с плагином `pgoutput`, без SQL polling.
- Разделить получение WAL-сообщений, их декодирование и доставку событий в целевую систему.
- Обрабатывать изменения с учётом границ транзакций (`BEGIN` / `COMMIT`).
- Читать только необходимые outbox-таблицы через отдельную publication.

### 2. Автоматическое управление replication slot

**Создавать replication slot при первом запуске CDC-сервиса, а не во время миграции базы данных.**

Причины:

- С момента создания слот может удерживать WAL, даже если CDC-сервис ещё не запущен. Создание слота заранее в миграции создаёт риск неконтролируемого роста WAL.
- Управление жизненным циклом слота логически относится к CDC-сервису, а не к схеме базы данных.
- Сервис может самостоятельно проверять существование слота, его конфигурацию и пригодность для продолжения репликации.

Правила:

- Создание слота должно быть идемпотентным.
- При перезапуске существующий слот переиспользуется и не удаляется при остановке сервиса.
- Если слот отсутствует, но сохранён checkpoint предыдущей репликации, автоматически пересоздавать его нельзя — это может привести к потере событий.
- Миграции должны создавать необходимые таблицы и publication. До создания слота нельзя допускать появления событий, которые сервис обязан доставить: новый слот не обеспечивает чтение уже существовавших изменений.

### 3. Управление LSN и подтверждение обработки

**Разделять позицию прочитанного WAL и позицию надёжно доставленных событий.**

- Подтверждать LSN PostgreSQL только после успешной записи событий в целевую систему и сохранения соответствующего checkpoint.
- Предпочтительно фиксировать прогресс на границах полностью обработанных транзакций.
- Учитывать, что несколько изменений могут иметь одинаковый LSN, а порядок WAL-позиций отдельных изменений не всегда соответствует порядку завершения транзакций.
- Продвижение подтверждённой позиции должно быть монотонным.

### 4. Восстановление после сбоев

- Сохранять checkpoint в устойчивом хранилище и возобновлять чтение с последней безопасной позиции.
- CDC-сервис должен обеспечивать **at-least-once delivery**: не терять события при сбоях, допуская повторную доставку.
- Дедупликация и идемпотентная бизнес-обработка выполняются на стороне потребителя через Inbox и не входят в ответственность CDC-сервиса.
- Если replication slot или необходимая позиция WAL недоступны, сервис должен остановить репликацию с явной ошибкой, а не незаметно пропускать изменения.

### 5. Backpressure и управление памятью

- Использовать ограниченную очередь между чтением WAL и доставкой событий.
- Если целевая система не успевает принимать события, замедлять обработку входящего потока и не подтверждать необработанные LSN.
- Не допускать неограниченного накопления событий в памяти.
- Размер очереди, размер батчей и параметры повторных попыток доставки должны быть конфигурируемыми.

### 6. Эксплуатационная надёжность

- Мониторинг задержки репликации, `restart_lsn`, `confirmed_flush_lsn` и объёма удерживаемого WAL.
- Автоматическое переподключение с backoff и восстановлением из checkpoint.
- Только один активный потребитель для каждого replication slot.
- Корректное завершение работы с сохранением подтверждённого прогресса.
- Явная обработка потери replication slot, недоступности WAL и переключения PostgreSQL на резервный сервер.

### Ключевые архитектурные принципы (часть I)

**CDC-сервис отвечает за надёжную доставку, а не за идемпотентную обработку событий.**

Разделение ответственности:

- **Outbox** — атомарное создание события вместе с бизнес-транзакцией.
- **CDC** — чтение WAL и доставка событий с гарантией at-least-once.
- **Inbox** — дедупликация и идемпотентная бизнес-обработка.

Основа надёжной реализации — автоматическое управление replication slot, корректные checkpoints, разделение чтения и подтверждения LSN, восстановление после сбоев и контролируемый backpressure.

Главный принцип: **PostgreSQL не должен получать подтверждение обработки WAL раньше, чем соответствующие события надёжно сохранены в целевой системе.**

# Часть II. Публикация CDC-событий в Kafka

### 1. Асинхронная пакетная публикация

- Использовать стандартный Kafka Producer с асинхронной отправкой сообщений.
- Не ожидать подтверждения каждого сообщения перед отправкой следующего. Передавать события пачками, используя встроенные механизмы batching Kafka Producer.
- **Успешный вызов отправки не означает доставку сообщения.** Событие считается опубликованным только после получения положительного подтверждения от Kafka.

### 2. Гарантии надёжной доставки

Настроить Kafka Producer для надёжной публикации:

- `acks=all` — ожидание подтверждения от всех реплик из ISR.
- `enable.idempotence=true` — защита от дублирования при внутренних повторах отправки producer.
- Настроить `delivery.timeout.ms`, retries и `min.insync.replicas` на стороне Kafka.

- Идемпотентность Kafka Producer не исключает повторной публикации после перезапуска CDC-сервиса.
- **CDC-сервис должен обеспечивать at-least-once delivery.** Дедупликация событий остаётся ответственностью Inbox.

### 3. Порядок публикации и подтверждения событий

- Сохранять исходный порядок событий при отправке в одну Kafka partition.
- Использовать стабильный Kafka message key, например `aggregate_id`, чтобы связанные события попадали в одну partition и сохраняли порядок.
- Отслеживать результаты асинхронных отправок. Если более поздние сообщения успешно опубликованы, но предыдущее ещё не подтверждено, нельзя продвигать checkpoint за неподтверждённое событие.
- **Предпочтительно подтверждать прогресс на границах полностью опубликованных PostgreSQL-транзакций.**

### 4. Связь Kafka ACK, checkpoint и LSN

Разделять три независимые операции:

1. **Kafka ACK** — подтверждение успешной публикации события.
2. **Checkpoint** — устойчивое сохранение последней полностью доставленной позиции WAL.
3. **LSN flush** — подтверждение PostgreSQL позиции, до которой события надёжно обработаны.

Правила:

- Сохранять checkpoint только после получения Kafka ACK для всех событий соответствующего диапазона WAL.
- Подтверждать LSN PostgreSQL только после успешного сохранения checkpoint.
- Нельзя продвигать LSN на основании отправки сообщений в буфер Kafka Producer или частичного успеха публикации.

### 5. Восстановление после сбоев

- После перезапуска возобновлять чтение WAL с последнего устойчивого checkpoint.
- Учитывать сценарии:
  - сбой до Kafka ACK — событие может быть отправлено повторно;
  - сбой после Kafka ACK, но до checkpoint — возможна повторная публикация уже доставленного события;
  - сбой после checkpoint, но до LSN flush — восстановление выполняется с сохранённой позиции без потери подтверждённых событий.
- Не пытаться обеспечивать exactly-once между PostgreSQL и Kafka средствами обычного producer. Основная гарантия CDC-сервиса — at-least-once.

### 6. Backpressure и управление ресурсами

- Использовать ограниченную очередь между WAL Reader и Kafka Publisher.
- Ограничивать количество и общий объём сообщений, одновременно ожидающих Kafka ACK.
- Если Kafka не успевает принимать события, замедлять чтение WAL через backpressure.
- Не допускать неограниченного накопления событий в памяти. Размер пачек, очередей и допустимое количество in-flight сообщений должны быть конфигурируемыми.

### 7. Обработка ошибок и эксплуатационная надёжность

- Автоматические повторные попытки при временных ошибках Kafka с ограничениями по времени.
- Остановку публикации и продвижения checkpoint при неисправимой ошибке доставки.
- Корректное завершение работы с ожиданием подтверждений уже отправленных сообщений.
- Мониторинг задержки публикации, количества ожидающих ACK сообщений, ошибок producer и отставания подтверждённого LSN.
- Явную обработку недоступности Kafka, отсутствующих топиков и ошибок сериализации.

### Ключевые архитектурные принципы (часть II)

**Публикация в Kafka и подтверждение PostgreSQL LSN должны быть связаны через устойчивый checkpoint.**

Последовательность:

```
WAL Read → Kafka Send → Kafka ACK → Durable Checkpoint → LSN Flush
```

При этом чтение WAL и отправка в Kafka могут выполняться асинхронно, но продвижение checkpoint должно учитывать только непрерывный диапазон полностью доставленных событий.

Главный принцип: **ни checkpoint, ни подтверждённый LSN не должны опережать фактически подтверждённую Kafka доставку.**

Это обеспечивает надёжную at-least-once репликацию без распределённых транзакций между PostgreSQL и Kafka.
