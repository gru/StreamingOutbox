# recommendations.md — рекомендации по реализации CDC-сервиса

Рекомендации основаны на инженерных подходах Debezium (Debezium Connector / Debezium Server Kafka Sink) и ориентированы на собственный CDC-сервис для высоконагруженных outbox-таблиц. Вместе с `dependencies.md` образуют проектную основу реализации: `dependencies.md` — стек и схема, этот файл — архитектура и гарантии доставки.

---

# Часть I. CDC-сервис на PostgreSQL

### 1. Чтение через Logical Replication Protocol

- Использовать стандартный PostgreSQL Logical Replication Protocol с плагином `pgoutput`, без SQL polling.
- Разделить получение WAL-сообщений, их декодирование и доставку событий в целевую систему.
- Обрабатывать изменения с учётом границ транзакций (`BEGIN` / `COMMIT`).
- Читать только необходимые outbox-таблицы через отдельную publication.

### 2. Автоматическое управление replication slot

**Создавать replication slot при первом запуске CDC-сервиса, а не во время миграции базы данных.**

Причины:

- С момента создания слот может удерживать WAL, даже если CDC-сервис ещё не запущен. Создание слота заранее в миграции создаёт риск неконтролируемого роста WAL.
- Управление жизненным циклом слота логически относится к CDC-сервису, а не к схеме базы данных.
- Сервис может самостоятельно проверять существование слота, его конфигурацию и пригодность для продолжения репликации.

Правила:

- Создание слота должно быть идемпотентным.
- При перезапуске существующий слот переиспользуется и не удаляется при остановке сервиса.
- Если слот отсутствует, но сохранён checkpoint предыдущей репликации, автоматически пересоздавать его нельзя — это может привести к потере событий.
- Опережение checkpoint'ом `confirmed_flush` слота при живом слоте — не терминальное состояние: checkpoint фиксируется в одной транзакции с доставкой, поэтому данные до опережающей позиции уже находятся в целевой системе. Продолжать с позиции слота с предупреждением, пере-доставляя окно между позициями (at-least-once). Терминальны только отсутствие слота при живом checkpoint и пустой `confirmed_flush` (обоснование всех вариантов — раздел «Согласование checkpoint-стора с replication slot при старте»).
- Миграции должны создавать необходимые таблицы и publication. До создания слота нельзя допускать появления событий, которые сервис обязан доставить: новый слот не обеспечивает чтение уже существовавших изменений.

### 3. Управление LSN и подтверждение обработки

**Разделять позицию прочитанного WAL и позицию надёжно доставленных событий.**

- Подтверждать LSN PostgreSQL только после успешной записи событий в целевую систему и сохранения соответствующего checkpoint.
- Предпочтительно фиксировать прогресс на границах полностью обработанных транзакций.
- Учитывать, что несколько изменений могут иметь одинаковый LSN, а порядок WAL-позиций отдельных изменений не всегда соответствует порядку завершения транзакций.
- Продвижение подтверждённой позиции должно быть монотонным.

### 4. Восстановление после сбоев

- Сохранять checkpoint в устойчивом хранилище и возобновлять чтение с последней безопасной позиции.
- CDC-сервис должен обеспечивать **at-least-once delivery**: не терять события при сбоях, допуская повторную доставку.
- Дедупликация и идемпотентная бизнес-обработка выполняются на стороне потребителя через Inbox и не входят в ответственность CDC-сервиса.
- Если replication slot или необходимая позиция WAL недоступны, сервис должен остановить репликацию с явной ошибкой, а не незаметно пропускать изменения.

### 5. Backpressure и управление памятью

- Использовать ограниченную очередь между чтением WAL и доставкой событий.
- Если целевая система не успевает принимать события, замедлять обработку входящего потока и не подтверждать необработанные LSN.
- Не допускать неограниченного накопления событий в памяти.
- Размер очереди, размер батчей и параметры повторных попыток доставки должны быть конфигурируемыми.

### 6. Эксплуатационная надёжность

- Мониторинг задержки репликации, `restart_lsn`, `confirmed_flush_lsn` и объёма удерживаемого WAL.
- Автоматическое переподключение с backoff и восстановлением из checkpoint.
- Только один активный потребитель для каждого replication slot.
- Корректное завершение работы с сохранением подтверждённого прогресса.
- Явная обработка потери replication slot, недоступности WAL и переключения PostgreSQL на резервный сервер.

### Ключевые архитектурные принципы (часть I)

**CDC-сервис отвечает за надёжную доставку, а не за идемпотентную обработку событий.**

Разделение ответственности:

- **Outbox** — атомарное создание события вместе с бизнес-транзакцией.
- **CDC** — чтение WAL и доставка событий с гарантией at-least-once.
- **Inbox** — дедупликация и идемпотентная бизнес-обработка.

Основа надёжной реализации — автоматическое управление replication slot, корректные checkpoints, разделение чтения и подтверждения LSN, восстановление после сбоев и контролируемый backpressure.

Главный принцип: **PostgreSQL не должен получать подтверждение обработки WAL раньше, чем соответствующие события надёжно сохранены в целевой системе.**

# Часть II. Публикация CDC-событий в Kafka

### 1. Асинхронная пакетная публикация

- Использовать стандартный Kafka Producer с асинхронной отправкой сообщений.
- Не ожидать подтверждения каждого сообщения перед отправкой следующего. Передавать события пачками, используя встроенные механизмы batching Kafka Producer.
- **Успешный вызов отправки не означает доставку сообщения.** Событие считается опубликованным только после получения положительного подтверждения от Kafka.

### 2. Гарантии надёжной доставки

Настроить Kafka Producer для надёжной публикации:

- `acks=all` — ожидание подтверждения от всех реплик из ISR.
- `enable.idempotence=true` — защита от дублирования при внутренних повторах отправки producer.
- Настроить `delivery.timeout.ms`, retries и `min.insync.replicas` на стороне Kafka.

- Идемпотентность Kafka Producer не исключает повторной публикации после перезапуска CDC-сервиса.
- **CDC-сервис должен обеспечивать at-least-once delivery.** Дедупликация событий остаётся ответственностью Inbox.

### 3. Порядок публикации и подтверждения событий

- Сохранять исходный порядок событий при отправке в одну Kafka partition.
- Использовать стабильный Kafka message key, например `aggregate_id`, чтобы связанные события попадали в одну partition и сохраняли порядок.
- Отслеживать результаты асинхронных отправок. Если более поздние сообщения успешно опубликованы, но предыдущее ещё не подтверждено, нельзя продвигать checkpoint за неподтверждённое событие.
- **Предпочтительно подтверждать прогресс на границах полностью опубликованных PostgreSQL-транзакций.**

### 4. Связь Kafka ACK, checkpoint и LSN

Разделять три независимые операции:

1. **Kafka ACK** — подтверждение успешной публикации события.
2. **Checkpoint** — устойчивое сохранение последней полностью доставленной позиции WAL.
3. **LSN flush** — подтверждение PostgreSQL позиции, до которой события надёжно обработаны.

Правила:

- Сохранять checkpoint только после получения Kafka ACK для всех событий соответствующего диапазона WAL.
- Подтверждать LSN PostgreSQL только после успешного сохранения checkpoint.
- Нельзя продвигать LSN на основании отправки сообщений в буфер Kafka Producer или частичного успеха публикации.

### 5. Восстановление после сбоев

- После перезапуска возобновлять чтение WAL с последнего устойчивого checkpoint.
- Учитывать сценарии:
  - сбой до Kafka ACK — событие может быть отправлено повторно;
  - сбой после Kafka ACK, но до checkpoint — возможна повторная публикация уже доставленного события;
  - сбой после checkpoint, но до LSN flush — восстановление выполняется с сохранённой позиции без потери подтверждённых событий.
- Не пытаться обеспечивать exactly-once между PostgreSQL и Kafka средствами обычного producer. Основная гарантия CDC-сервиса — at-least-once.

### 6. Backpressure и управление ресурсами

- Использовать ограниченную очередь между WAL Reader и Kafka Publisher.
- Ограничивать количество и общий объём сообщений, одновременно ожидающих Kafka ACK.
- Если Kafka не успевает принимать события, замедлять чтение WAL через backpressure.
- Не допускать неограниченного накопления событий в памяти. Размер пачек, очередей и допустимое количество in-flight сообщений должны быть конфигурируемыми.

### 7. Обработка ошибок и эксплуатационная надёжность

- Автоматические повторные попытки при временных ошибках Kafka с ограничениями по времени.
- Остановку публикации и продвижения checkpoint при неисправимой ошибке доставки.
- Корректное завершение работы с ожиданием подтверждений уже отправленных сообщений.
- Мониторинг задержки публикации, количества ожидающих ACK сообщений, ошибок producer и отставания подтверждённого LSN.
- Явную обработку недоступности Kafka, отсутствующих топиков и ошибок сериализации.

### Ключевые архитектурные принципы (часть II)

**Публикация в Kafka и подтверждение PostgreSQL LSN должны быть связаны через устойчивый checkpoint.**

Последовательность:

```
WAL Read → Kafka Send → Kafka ACK → Durable Checkpoint → LSN Flush
```

При этом чтение WAL и отправка в Kafka могут выполняться асинхронно, но продвижение checkpoint должно учитывать только непрерывный диапазон полностью доставленных событий.

Главный принцип: **ни checkpoint, ни подтверждённый LSN не должны опережать фактически подтверждённую Kafka доставку.**

Это обеспечивает надёжную at-least-once репликацию без распределённых транзакций между PostgreSQL и Kafka.

### Сохранение checkpoint и восстановление после сбоев

Сервис должен сохранять checkpoint в устойчивом хранилище, чтобы после перезапуска продолжать чтение WAL без потери событий.

Алгоритм работы:

1. **Чтение и публикация.** Сервис читает изменения из replication slot и асинхронно публикует события в Kafka, отслеживая успешность их доставки.

2. **Определение безопасной позиции.** После получения подтверждений от Kafka сервис определяет последнюю позицию WAL, до которой все события гарантированно опубликованы. Нельзя продвигать checkpoint, если остались неподтверждённые более ранние события. Предпочтительно использовать границы полностью обработанных транзакций.

3. **Сохранение checkpoint.** Безопасная позиция периодически сохраняется в устойчивом хранилище. Это позволяет не выполнять отдельную запись после каждого события и уменьшить накладные расходы.

4. **Подтверждение PostgreSQL.** Только после успешного сохранения checkpoint сервис подтверждает соответствующий LSN PostgreSQL, разрешая освободить больше не нужные WAL-записи.

5. **Восстановление после перезапуска.** Сервис загружает последний сохранённый checkpoint, проверяет его согласованность с состоянием replication slot и возобновляет чтение с безопасной позиции, учитывая границы транзакций. Если необходимый WAL недоступен, репликация останавливается с явной ошибкой.

6. **Повторная доставка.** Если сбой произошёл после публикации в Kafka, но до сохранения checkpoint, часть событий будет опубликована повторно. Это ожидаемое поведение при гарантии at-least-once. Дедупликация остаётся ответственностью Inbox.

**Ключевой принцип:** checkpoint отражает только надёжно доставленные события, а подтверждённый PostgreSQL LSN никогда не должен опережать устойчиво сохранённый checkpoint. Это позволяет восстанавливать работу после сбоев без потери событий, допуская повторную доставку.

### Checkpoint Store в Kafka

Для хранения checkpoint использовать отдельный Kafka topic с включённым log compaction, обеспечивающим сохранение последнего актуального состояния для каждого CDC-источника.

Требования:

- Сохранять checkpoint под стабильным идентификатором источника репликации, чтобы после перезапуска или переноса сервиса на другой инстанс можно было восстановить прогресс.
- Записывать checkpoint только после подтверждённой доставки соответствующих событий в Kafka.
- Считать checkpoint сохранённым только после успешного подтверждения записи со стороны Kafka.
- При запуске загружать последний сохранённый checkpoint и проверять его совместимость с текущим состоянием replication slot.
- Обеспечить долговременное хранение checkpoint независимо от жизненного цикла экземпляров CDC-сервиса.

### Recovery Mode

Предусмотреть специальный флаг `recovery_mode`, позволяющий вручную восстановить работу CDC-сервиса при невозможности продолжить репликацию с сохранённого checkpoint.

Требования:

- **В обычном режиме** сервис останавливается с явной ошибкой только при несовместимости, означающей недоставленное окно, которое нечем прочитать: слот отсутствует при живом checkpoint или `confirmed_flush` слота пуст. Опережение checkpoint'ом `confirmed_flush` при живом слоте к этому классу не относится (данные до checkpoint уже доставлены) — сервис продолжает с позиции слота с предупреждением и пере-доставкой окна (at-least-once).
- **При включённом Recovery Mode** сервис игнорирует устаревший checkpoint и начинает репликацию с текущей доступной позиции replication slot. Если слот отсутствует или непригоден, допускается его пересоздание с текущей позиции PostgreSQL.
- Перед началом репликации сервис сохраняет новый checkpoint, соответствующий выбранной позиции, чтобы последующие перезапуски могли происходить в обычном режиме.
- Использование Recovery Mode должно явно отражаться в логах и метриках с указанием предыдущей и новой позиции репликации.
- Recovery Mode должен использоваться только для ручного аварийного восстановления, а не как автоматическая стратегия обработки ошибок.

**Важно:** Recovery Mode допускает пропуск событий между последней корректно обработанной позицией и новой точкой старта. Это осознанный отказ от гарантии доставки пропущенных событий, поэтому включение режима должно быть явным решением оператора.

### Согласование checkpoint-стора с replication slot при старте (обоснование стратегии)

Стратегия согласования опирается на инвариант конвейера: **checkpoint фиксируется в одной транзакции с доставкой** (батч событий несёт checkpoint-запись; финальное и recovery-сохранения выполняются по уже доставленной позиции), а **позиция слота подтверждается только после подтверждённого commit checkpoint** (порядок «ACK → durable checkpoint → подтверждение»). Следствия: закоммиченный checkpoint на позиции Y — доказательство доставки всех событий до Y; `confirmed_flush` никогда не опережает последнюю закоммиченную checkpoint-запись в исполнении самого сервиса.

Матрица состояний старта и выбор для каждого:

| Состояние на старте | Стратегия | Обоснование |
| --- | --- | --- |
| checkpoint отсутствует | продолжение (первый запуск / пересоздание checkpoint-топика) | согласовывать нечего; позиция чтения — слот |
| checkpoint == confirmed_flush | продолжение штатное | состояния согласованы |
| checkpoint опережает confirmed_flush, слот жив | продолжение с позиции слота + предупреждение | данные до checkpoint уже в целевой системе — доказательство доставки есть сам факт закоммиченного checkpoint; слот лишь отстал с подтверждением позиции |
| confirmed_flush опережает checkpoint | продолжение с позиции слота | сервисом недостижимо (инвариант выше); возникает только от внешних действий (ручной advance слота, пересоздание/усечение checkpoint-топика, запись другой инсталляции) или устаревшего чтения топика; читать назад от позиции слота невозможно в любом случае |
| слот отсутствует, checkpoint жив | терминальная ошибка → явный Recovery Mode | единственное состояние с реальным недоставленным окном, которое нечем прочитать: новый слот начал бы с текущей позиции WAL и молча пропустил бы окно — такое решение не может быть автоматическим |
| confirmed_flush пуст | терминальная ошибка | слот непригоден, позиция неопределима |

Почему опережение при живом слоте — не терминальная ошибка. Страх «WAL между позициями мог быть переработан» проверяет не сервис, а сервер: если WAL у позиции слота отсутствует, PostgreSQL сам отказывает в чтении явной терминальной ошибкой (инвалидированный слот / запрошенный WAL-сегмент удалён) — потеря не замалчивается, а переносится из априорного запрета в факт от сервера. Последствия продолжения: на одном таймлайне окно между позициями пере-доставляется дублями (at-least-once, дедупликация — ответственность потребителя); при восстановлении БД на новом таймлайне (слот пересоздан, окна в новом WAL нет) пере-доставки нет — сервис продолжает с позиции слота, а первый доставленный батч перезаписывает checkpoint-запись (текущее значение — последняя запись ключа, оно следует таймлайну слота).

Сценарии попадания в опережение при живом слоте (все безопасны по инварианту):

- гонка финального checkpoint при остановке: бюджет ожидания ридера истёк, серверу подтверждена последняя сохранённая позиция, а находящаяся в полёте финальная транзакция checkpoint докоммитилась после возврата целевой системы; окно гонки — между бюджетом ожидания ридера и таймаутом операции commit;
- PostgreSQL недоступен в момент остановки (целевая система доступна): checkpoint сохранён, финальное подтверждение позиции не доставлено;
- жёсткое прерывание процесса в зазоре между commit checkpoint и немедленным подтверждением позиции слота (микроокно, существует всегда);
- отставание синхронизированной failover-копии слота после смены primary (штатное состояние failover-слотов);
- восстановление БД из копии на новом таймлайне.

Отклонённые альтернативы:

- **терминальная ошибка на опережении** (прежнее поведение) — ложные аварии при доказанно доставленных данных: приёмка задачи 11 — оба экземпляра Active-Passive остановились после полного отказа Kafka с «checkpoint опережает confirmed_flush», при этом доставка была полной и вердикт прогона — pass;
- **предотвращение самой гонки** — commit транзакции в клиенте синхронный и не принимает отмену; попытка откатить транзакцию в полёте создаёт собственную гонку; состояние также достижимо путями, не связанными с остановкой (см. сценарии);
- **порог по размеру разрыва** — размер не коррелирует с опасностью (широкое штатное окно и узкое аварийное одинаково безопасны по инварианту); единственный содержательный вопрос «существует ли WAL окна» отвечает сервер при чтении;
- **терминализация «confirmed_flush опережает checkpoint»** — Recovery Mode на это состояние отвечает «рассогласования нет» (неисправимый тупик: обычный старт терминален, recovery бездействует); устаревшее чтение checkpoint-топика при деградации целевой системы фабриковало бы терминал из артефакта чтения; перекрёстный опыт Debezium (ниже) подтверждает;
- **автоперезапись checkpoint вниз при штатном старте** — лишняя транзакция на получении лидерства ради косметики: первый доставленный батч перезаписывает запись.

Ссылки на документацию PostgreSQL (физическая невозможность перемотки слота назад): `pg_replication_slot_advance` не двигает слот назад («The slot will not be moved backwards»); функции и протокол создания слота не принимают стартовую позицию (новый слот начинается с текущей позиции WAL); `START_REPLICATION SLOT … LOGICAL` стартует с max(запрошенный LSN, confirmed_flush) — передать более раннюю позицию нельзя.

Перекрёстная проверка — Debezium 3.4: свойство `offset.mismatch.strategy` (`no_validation` — по умолчанию / `trust_offset` / `trust_slot` / `trust_greater_lsn`) и `lsn.flush.mode=connector` (подтверждать LSN только после устойчивого сохранения offsets — тот же порядок, что и здесь). История Debezium показательна: строгая проверка «Saved offset is before replication slot's confirmed lsn» приводила к ложным авариям и полным повторным снимкам данных при нулевой фактической потере (сценарий с keepalive-подтверждениями позиции эксплуатировался годами без потерь), в итоге сообществом выбраны стратегии доверия слоту/максимуму. Выбор здесь эквивалентен `trust_slot` с журналированием (предупреждение при опережении) и строже умолчания Debezium (`no_validation` — без проверки вовсе); терминальными остаются состояния, для которых у Debezium аналога нет (утраченный слот при живом checkpoint).

## Балансировка CDC-экземплясов через Kafka

Для обеспечения отказоустойчивости использовать модель **Active-Passive** на основе Kafka Consumer Group и общего Checkpoint Store.

### 1. Выбор активного экземпляра

- Создать служебный Kafka topic `cdc-checkpoints` ровно с **одной** partition (контракт заморожен — см. подраздел «Несколько слотов на общем checkpoint-топике») и `cleanup.policy=compact`.
- Все экземпляры, обслуживающие один replication slot (пара Active-Passive), подключаются к одной Consumer Group — **группа принадлежит слоту**: формула `cdc-outbox-<slot>` (решение владельца 2026-11-06, реализована задачей 15), одинакова у обоих экземпляров пары, группы разных слотов не пересекаются.
- Экземпляр, которому Kafka назначила partition, становится активным (при единственной партиции топика назначение одно — лидер ровно один). Остальные работают в standby-режиме и поддерживают членство в группе.
- Только активный экземпляр имеет право подключаться к PostgreSQL replication slot, читать WAL и публиковать события.

### 2. Связь с Checkpoint Store

- После получения лидерства экземпляр инициализирует Kafka transactional producer с постоянным `transactional.id`, привязанным к replication slot. Это блокирует транзакционные записи предыдущего лидера.
- Новый лидер загружает последний checkpoint из `cdc-checkpoints`, используя `read_committed`, проверяет состояние replication slot и возобновляет чтение.
- CDC-события асинхронно публикуются в Kafka с гарантией at-least-once.
- После Kafka ACK для непрерывного диапазона событий лидер транзакционно сохраняет новый checkpoint в `cdc-checkpoints`.
- Только после успешного commit checkpoint подтверждает соответствующий LSN PostgreSQL.

### 3. Переключение при сбоях

- При отказе активного экземпляра Kafka выполняет rebalance и назначает partition другому экземпляру.
- Новый лидер выполняет fencing предыдущего producer, загружает checkpoint и подключается к replication slot.
- Если слот ещё занят прежним соединением, новый лидер ожидает его освобождения.
- При потере лидерства или обнаружении fencing прежний экземпляр прекращает чтение, публикацию и обновление checkpoint.
- Возможна повторная доставка событий, опубликованных после последнего сохранённого checkpoint. Это соответствует гарантии at-least-once.

**Ошибки запуска при получении лидерства** (фикс 2026-11-05, заказ владельца: хост не останавливается на ошибках, восстановимых в перспективе). Запуск доставки нового периода лидерства — инициализация транзакционного продюсера и стартовые проверки — сам подвержен транзиентным сбоям среды: приёмка задачи 11 поймала обрыв PG-чтения в момент проверок (`Npgsql EndOfStreamException` после полного outage Kafka) — catch-all координатора объявил его терминальным, хост остановился, а рестарт-политики у пары нет — экземпляр лежал до ручного подъёма, хотя повтор через секунды прошёл бы. Принцип — тот же, что в доставке: восстановимые ошибки не останавливают хост, а повторяются с backoff (`RetryDelaySeconds`/`MaxRetryDelaySeconds`, каждая попытка со свежим DI-скоупом), лидерство при этом удерживается — причина сбоя общая для пары (одни PG/Kafka), standby доставил бы не раньше; локальные причины (мёртвое пул-соединение) излечиваются самим повтором. Терминальные нарушения стартовых проверок остаются остановкой хоста: классификация живёт в типе исключения — `StartupCheckException` (слота нет при живом checkpoint, пустой `confirmed_flush`, чужой плагин, отсутствие publication/checkpoint-topic, `wal_level` < logical, битая запись стора) — оператор должен вмешаться, повторения бессмысленны; остановка заодно освобождает группу — standby получает лидерство и свой шанс. Сетевые ветки проверок (недоступность метадаты Kafka, неудавшееся чтение checkpoint-стора, `pg_is_in_recovery` в окне failover) остаются обычными исключениями и потому повторяются.

### 4. Обязательные ограничения

- Для каждого replication slot использовать стабильный идентификатор checkpoint и `transactional.id`.
- Служебный Kafka Consumer должен регулярно выполнять `poll()`, независимо от работы WAL Reader.
- Checkpoint при восстановлении читать как последнее актуальное значение из topic, а не использовать consumer group offset.
- Не допускать продвижения checkpoint при неподтверждённых более ранних событиях.
- Старый экземпляр не должен повторно инициализировать transactional producer после потери лидерства.
- Контрольная группа — одна на слот (`cdc-outbox-<slot>`); экземпляры разных слотов никогда не смешиваются в одну группу: на однопартиционном топике общая группа оставила бы все слоты, кроме одного, без лидера.

**Ключевой принцип:** Kafka Consumer Group определяет активный экземпляр, transactional producer защищает checkpoint от устаревших экземпляров, а PostgreSQL replication slot обеспечивает эксклюзивное чтение WAL.

Решение: в качестве стабильного идентификатора checkpoint используется **имя replication slot** (в стенде — `outbox_slot`); от него же зависят постоянный `transactional.id` и контрольная группа арбитража — формула `cdc-outbox-<slot>` (группа — реализована задачей 15, решение владельца 2026-11-06).

### 5. Несколько слотов на общем checkpoint-топике (контракт задачи 15, решение владельца 2026-11-06)

Топик `cdc-checkpoints` общий для многих слотов: слотов много, у каждого — своя пара Active-Passive (один экземпляр обслуживает строго один слот — решение владельца 2026-11-04). Контракт:

- **Группа — на слот, не на кластер.** Контрольная consumer group принадлежит слоту: формула `cdc-outbox-<slot>`, одинакова у обоих экземпляров пары. Kafka назначает партиции каждой группе независимо — выборы разных слотов друг на друга не влияют, переключение одной пары не трогает другую. Разделение обязательно: на однопартиционном топике общая группа на все пары даёт одного лидера на весь кластер — все слоты, кроме одного, без доставки.
- **Партиций ровно одна — контракт заморожен.** Ключ записи — имя слота: очистка журнала по ключу (compaction) изолирует значения слотов, чтение последнего checkpoint — скан партиции с фильтром по ключу. Арбитражу партиции не нужны, а модель «любое назначение партиции = лидерство» корректна только при единственной партиции: при N > 1 оба члена пары получают по части партиций — лидеров двое.
- **Отклонённая альтернатива — многопартиционность с маршрутизацией по ключу-слоту.** (1) Общая группа на все пары при «один экземпляр = один слот» неработоспособна: assignor не знает слотов — партиция слота может достаться экземпляру чужой пары, а при числе членов больше числа партиций часть пар остаётся без назначений целиком. (2) При группах-на-слот многопартиционность даёт лишь изоляцию скана `ReadLatest` и параллельность очистки журнала — при объёмах checkpoint-записей (сотни байт раз в интервал сохранения на слот) выигрыш маргинален. (3) Цена: координатор обязан распознавать партицию своего слота (не «любую назначенную»), маршрутизация записи и чтения обязана быть согласована, а число партиций keyed-топика фактически заморожено — добавление партиций перемешивает маршрутизацию, старые записи слота остаются в прежних партициях и чтение своей партиции теряет историю.

### Fencing: термин и семантика

**Fencing (букв. «огораживание»)** — механизм распределённых систем, который гарантирует, что **устаревший владелец ресурса физически не может записать ничего после того, как право владения перешло к новому**. Проблема, которую он решает: «зомби» — участник, живой процесс которого считает себя владельцем (не заметил отказа сети, потери роли), и чья запись, будучи устаревшей, могла бы перезаписать прогресс нового владельца (stale write). Fencing блокирует такого участника на **стороне арбитра**, не рассчитывая на его «вежливое» добровольное прекращение работы.

Свойства, отличающие fencing от простой координации:

1. **Односторонняя гарантия**: после появления нового владельца старый не пишет; обратное не требуется — пока нового нет, старый писать вправе (это «окно зомби», оно не обязано быть нулевым; в нашей паре оно безопасно: зомби в нём — единственный пишущий, его прогресс реален и монотонен).
2. **Ровно одна валидная эпоха**: владение идентифицируется стабильным идентификатором линии с монотонным номером поколения (эпохой), переживающим рестарты процессов.
3. **Не зависит от сотрудничества старого владельца**: узнаёт он о блокировке или нет — его записи всё равно отвергаются; узнаёт он, как правило, только попыткой записи.

**Реализация в Kafka (наш случай).** Идентификатор линии владения — `transactional.id` (стабилен между экземплярами и рестартами — иначе блокировать было бы некого и нечем). Эпоха (producerId + generation) хранится у координатора транзакций. **Акт fencingа** — `InitTransactions` нового владельца: он поднимает эпоху и синхронно закрывает висящую транзакцию предыдущей (маркеры abort в затронутые партиции, LSO вверх); именно поэтому fencing выполняется до чтения checkpoint — чтение `read_committed` не упирается в стену LSO зависшей транзакции. Всё, что старая эпоха пытается закоммитить после этого, отвергается (`InvalidProducerEpoch`/`ProducerFenced`; в .NET-клиенте это `KafkaException` с соответствующим кодом — отдельного типа исключения нет) — по этой ошибке сервис и узнаёт о потере лидерства. Отсюда правило «после потери лидерства — остановка без переинициализации продюсера»: переинициализация разрешена только при новом получении лидерства — она и есть fencing следующего владельца. Повторный `InitTransactions` на том же экземпляре невалиден (клиент уже в состоянии Ready), поэтому продюсер — сервис периода лидерства и на каждый период лидерства создаётся заново; смена экземпляра fencing не ослабляет: идентификатор стабилен, эпоха хранится у координатора (фикс дефекта, найденного приёмкой задачи 11).

**Защищаемая инварианта.** Fencing закрывает единственный путь отката checkpoint'а назад: зомби-лидер, записавший устаревший watermark последним (очистка журнала `cdc-checkpoints` по ключу хранит последнюю запись ключа) и обесценивший прогресс действующего лидера. После смены эпохи такой write невозможен; до неё — безопасен. Дополнительный эффект транзакций: события и checkpoint фиксируются атомарно, записи прерванных транзакций невидимы `read_committed`-читателям (валидатор переключён на `read_committed` именно поэтому).

**Три линии защиты пары Active-Passive** (термин в контексте системы): (1) **Kafka-транзакции** — блокируют запись устаревшего владельца (эту инварианту); (2) **consumer group на `cdc-checkpoints`** — распределяет права (кто лидер), сама по себе никого не блокирует; (3) **эксклюзивность replication slot PostgreSQL** (SQLSTATE 55006 на второго walsender) — последняя линия: два читателя одного слота невозможны, даже если координация Kafka ошиблась.

## Обновление PostgreSQL и восстановление CDC

При мажорном обновлении PostgreSQL значения LSN не гарантируют непрерывность между старым и новым кластером.

- При pg_upgrade с PostgreSQL 17 и выше логические слоты могут быть восстановлены с прежними именами, но с новыми значениями LSN.
- При pg_upgrade с более старых версий логические слоты не переносятся.
- При dump/restore логические слоты не переносятся и должны создаваться заново.

Поэтому перед миграцией необходимо завершить доставку всех накопленных событий, а после миграции согласовать checkpoint с новой стартовой позицией репликации.

### Контроль простоя потока (idle-предупреждение)

Специальный режим завершения доставки (drain) в сервисе не предусматривается (решение владельца): при отсутствии новых outbox-событий сервис продолжает штатную работу — держит слот, читает WAL и публикует всё, что появляется. Штатное завершение доставки перед остановкой обеспечивает корректное завершение работы с сохранением прогресса: дождаться Kafka ACK → сохранить checkpoint → подтвердить LSN (часть I §6, часть II §7).

Для наблюдаемости простоя сервис отслеживает время с последнего полученного события:

- Если новые outbox-события отсутствуют в течение настраиваемого интервала `idle_timeout`, сервис записывает предупреждение (WARN) в лог — не чаще одного раза за интервал.
- Любое новое событие сбрасывает таймер простоя; повторное истечение интервала снова записывает предупреждение.
- Предупреждение не останавливает репликацию и не меняет состояние сервиса, но сигнализирует о проблеме: без новых событий слот не подтверждается (confirmed_flush стоит на месте), и удерживаемый WAL может накапливаться. Heartbeat-механизм (периодическая пустая активность для продвижения позиции слота) в сервисе отсутствует — сознательное решение: streaming-outbox предназначен для «горячих» outbox с постоянной записью, затянувшийся простой — повод проверить запись в outbox (решение владельца 2026-11-02).

Назначение — операционный сигнал «поток пуст и слот не подтверждается». В частности, он используется при подготовке к обновлению PostgreSQL (см. порядок ниже): предупреждения в логе при остановленной записи означают, что накопленные события доставлены и новых не появляется.

### Порядок обновления PostgreSQL

1. Остановить бизнес-приложение или запретить создание новых outbox-событий.
2. Дождаться доставки накопленных событий: отставание checkpoint сходит к нулю, в логе появляются idle-предупреждения об отсутствии новых событий.
3. Остановить все экземпляры CDC (активный и резервные — штатная остановка сохраняет подтверждённый прогресс) либо отключить автоматическое назначение нового лидера.
4. Выполнить pg_upgrade или dump/restore.
5. Запустить CDC в режиме `recovery_mode`, позволяющем согласовать checkpoint с новой позицией слота или создать отсутствующий слот.
6. После успешного сохранения нового checkpoint и запуска чтения WAL вернуть CDC в обычный режим и возобновить работу бизнес-приложения.
