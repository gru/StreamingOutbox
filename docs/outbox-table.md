# outbox-table.md — таблица `outbox.messages`

Описание таблицы outbox для сервиса: назначение, структура, особенности, внутреннее представление сообщения и публикация в Kafka, связь с метриками. Канонический DDL и SQL-примеры (publication, failover-слот) — `dependencies.md` §3–5.

---

## Назначение

Таблица `outbox.messages` предназначена для хранения сообщений, которые должны быть асинхронно отправлены во внешнюю систему обмена сообщениями (например, Kafka).

Таблица используется для реализации паттерна Transactional Outbox, обеспечивающего надёжную отправку сообщений после их сохранения в базе данных.

Сообщения сохраняются в таблице в рамках транзакции, после чего Outbox-процессор считывает их и отправляет в брокер сообщений.

---

## Структура таблицы

| Поле               | Тип данных   | Обязательное | Описание                                                                                                                           |
| ------------------ | ------------ | ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `id`               | bigint       | Да           | Уникальный идентификатор сообщения. Генерируется автоматически. Первичный ключ таблицы.                                            |
| `topic`            | varchar(255) | Да           | Название топика, в который необходимо отправить сообщение.                                                                         |
| `key`              | bytea        | Да           | Ключ сообщения в бинарном формате. Может использоваться для определения партиции в брокере сообщений.                              |
| `body`             | bytea        | Да           | Содержимое сообщения в бинарном формате.                                                                                           |
| `headers`          | varchar      | Да           | Дополнительные заголовки сообщения, содержащие метаданные.                                                                         |
| `partition`        | integer      | Нет          | Номер партиции брокера сообщений, в которую необходимо отправить сообщение.                                                        |
| `producer_key`     | varchar(255) | Нет          | Идентификатор или ключ продюсера, используемого для отправки сообщения.                                                            |
| `created_at`       | timestamptz  | Да           | Дата и время создания сообщения. По умолчанию устанавливается текущее время (`now()`).                                             |
| `outbox_partition` | integer      | Да           | Номер внутренней партиции Outbox, используемой для распределения сообщений между экземплярами Outbox-процессора. По умолчанию `0`. |

> **Замечания по полям:**
>
> - **`producer_key`** — используется для выбора продюсера (кластера), через который выполняется публикация. В текущей реализации не используется.
> - **`outbox_partition`** — предназначено для внутреннего разделения сообщений Outbox; по умолчанию `0`. В текущей реализации не используется.

## Особенности таблицы

### 1. Уникальность сообщений

Поле `id` является первичным ключом (`PRIMARY KEY`) и обеспечивает уникальность каждой записи.

### 2. Поддержка партиционирования

В таблице предусмотрены два поля для партиционирования:

- `partition` — партиция брокера сообщений, в которую направляется сообщение.
- `outbox_partition` — логическая партиция Outbox для распределения обработки сообщений между процессорами.

### 3. Хранение сообщений

Поля `key` и `body` имеют тип `bytea`, позволяющий сохранять данные в бинарном формате независимо от используемого формата сериализации.

### 4. Отслеживание времени создания

Поле `created_at` позволяет определять время нахождения сообщения в Outbox и анализировать задержки его отправки.

### 5. Асинхронная обработка

Outbox-процессор считывает сохранённые сообщения и отправляет их в брокер. Механизм удаления или подтверждения успешно отправленных сообщений структурой таблицы не фиксируется — определяется реализацией Outbox-процессора.

## Внутреннее представление сообщения: `OutboxMessage`

Класс — внутреннее представление outbox-сообщения в сервисе; поля соответствуют колонкам таблицы. `outbox_partition` в представлении отсутствует — поле в текущей реализации не используется (см. замечания выше).

```csharp
/// <summary>
/// Outbox-сообщение.
/// </summary>
public class OutboxMessage
{
    /// <summary>
    /// Идентификатор сообщения.
    /// </summary>
    public long Id { get; set; }

    /// <summary>
    /// Название топика, в котором будет опубликовано сообщение.
    /// </summary>
    public string Topic { get; set; } = null!;

    /// <summary>
    /// Ключ сообщения.
    /// </summary>
    public byte[] Key { get; set; } = null!;

    /// <summary>
    /// Тело сообщения.
    /// </summary>
    public byte[] Body { get; set; } = null!;

    /// <summary>
    /// Заголовки сообщения.
    /// </summary>
    public string Headers { get; set; } = null!;

    /// <summary>
    /// Номер партиции, в которой будет опубликовано сообщение.
    /// </summary>
    public int? Partition { get; set; }

    /// <summary>
    /// Ключ producer-а.
    /// На основе значения данного свойства определяется
    /// producer (кластер) для публикации сообщения,
    /// сохраненного в outbox.
    /// </summary>
    public string? ProducerKey { get; set; }

    /// <summary>
    /// Дата и время сохранения сообщения в outbox.
    /// </summary>
    public DateTime CreatedAt { get; internal set; }
}
```

## Публикация в Kafka

Обязательный интерфейс-контракт транспорта публикации в проекте **не вводится** (решение владельца): публикация outbox-сообщений выполняется напрямую клиентом Confluent.Kafka (`dependencies.md` §2) из внутреннего представления `OutboxMessage` — без слоя-посредника, который ограничивал бы реализацию (батчинг, delivery-репорты, транзакционный продюсер checkpoint'ов на этапе резервирования). Отправка пакетная и асинхронная, с поддержкой отмены; параметры продюсера (`acks`, идемпотентность, батчинг, таймауты) фиксируются в конфигурации сервиса (план — `implementation-plan.md`, задачи 1 и 4).

## Настройки хранилища: `OutboxStorageOptions`

Класс настроек, позволяющий указать схему и таблицу outbox при настройке сервиса. Значения по умолчанию — каноническая таблица `outbox.messages` (`dependencies.md` §3).

```csharp
/// <summary>
/// Настройки хранилища Outbox.
/// </summary>
public class OutboxStorageOptions
{
    /// <summary>
    /// Схема таблицы outbox.
    /// </summary>
    public string Schema { get; set; } = "outbox";

    /// <summary>
    /// Имя таблицы outbox.
    /// </summary>
    public string Table { get; set; } = "messages";
}
```

## Формат тестового body (контракт Writer ↔ KafkaValidator)

Тестовый контур — генератор нагрузки Writer и валидатор доставки KafkaValidator — договорился о содержимом `body` и `key`. Общего кода между сервисами нет: контракт продублирован в коде каждого сервиса и зафиксирован здесь.

- `body` (bytea, UTF-8 JSON): `{"id": <bigint — id строки>, "runId": "<guid прогона>", "eventType": "TestEvent", "payload": "<строка заданной длины>", "timestamp": "yyyy-MM-ddTHH:mm:ss.fffZ"}`.
- `key` (bytea) = UTF-8 десятичного представления `id`.
- `headers` = `"{}"`; `partition`, `producer_key`, `outbox_partition` Writer не пишет (NULL/DEFAULT).

Идентичность сообщения при валидации — `body.id` (= `id` таблицы; см. «Запись тестовой нагрузки» в `dependencies.md` §3 — Writer резервирует id через `nextval` и вставляет с `OVERRIDING SYSTEM VALUE`). Группировка прогонов — `body.runId`. Дубликаты допустимы (at-least-once); потеря (`written` из Writer, отсутствующий в Kafka) и аномалии (`id` вне ожидаемого набора) фейлят вердикт валидатора.

## Краткое описание для технической документации

Таблица `outbox.messages` предназначена для временного хранения сообщений, подлежащих асинхронной отправке в брокер сообщений.

Каждая запись содержит уникальный идентификатор, топик назначения, ключ, тело сообщения, заголовки, параметры маршрутизации и время создания.

Для распределения нагрузки между экземплярами Outbox-процессора используется поле `outbox_partition`. Поле `partition` позволяет указать целевую партицию брокера сообщений.

Таблица является частью механизма Transactional Outbox, обеспечивающего согласованное сохранение бизнес-данных и сообщений в рамках одной транзакции при соответствующей реализации записи.
