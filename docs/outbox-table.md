# outbox-table.md — таблица `outbox.messages`

Описание таблицы outbox для сервиса: назначение, структура, особенности, внутреннее представление сообщения и публикация в Kafka, связь с метриками. Канонический DDL и SQL-примеры (publication, failover-слот) — `dependencies.md` §3–5.

---

## Назначение

Таблица `outbox.messages` предназначена для хранения сообщений, которые должны быть асинхронно отправлены во внешнюю систему обмена сообщениями (например, Kafka).

Таблица используется для реализации паттерна Transactional Outbox, обеспечивающего надёжную отправку сообщений после их сохранения в базе данных.

Сообщения сохраняются в таблице в рамках транзакции, после чего Outbox-процессор считывает их и отправляет в брокер сообщений.

---

## Структура таблицы

| Поле               | Тип данных   | Обязательное | Описание                                                                                                                           |
| ------------------ | ------------ | ------------ | ---------------------------------------------------------------------------------------------------------------------------------- |
| `id`               | bigint       | Да           | Уникальный идентификатор сообщения. Генерируется автоматически. Первичный ключ таблицы.                                            |
| `topic`            | varchar(255) | Да           | Название топика, в который необходимо отправить сообщение.                                                                         |
| `key`              | bytea        | Да           | Ключ сообщения в бинарном формате. Может использоваться для определения партиции в брокере сообщений.                              |
| `body`             | bytea        | Да           | Содержимое сообщения в бинарном формате.                                                                                           |
| `headers`          | varchar      | Да           | Дополнительные заголовки сообщения, содержащие метаданные.                                                                         |
| `partition`        | integer      | Нет          | Номер партиции брокера сообщений, в которую необходимо отправить сообщение.                                                        |
| `producer_key`     | varchar(255) | Нет          | Идентификатор или ключ продюсера, используемого для отправки сообщения.                                                            |
| `created_at`       | timestamptz  | Да           | Дата и время создания сообщения. По умолчанию устанавливается текущее время (`now()`).                                             |
| `outbox_partition` | integer      | Да           | Номер внутренней партиции Outbox, используемой для распределения сообщений между экземплярами Outbox-процессора. По умолчанию `0`. |

> **Замечания по полям:**
>
> - **`producer_key`** — используется для выбора продюсера (кластера), через который выполняется публикация. В текущей реализации не используется.
> - **`outbox_partition`** — предназначено для внутреннего разделения сообщений Outbox; по умолчанию `0`. В текущей реализации не используется.

## Особенности таблицы

### 1. Уникальность сообщений

Поле `id` является первичным ключом (`PRIMARY KEY`) и обеспечивает уникальность каждой записи.

### 2. Поддержка партиционирования

В таблице предусмотрены два поля для партиционирования:

- `partition` — партиция брокера сообщений, в которую направляется сообщение.
- `outbox_partition` — логическая партиция Outbox для распределения обработки сообщений между процессорами.

### 3. Хранение сообщений

Поля `key` и `body` имеют тип `bytea`, позволяющий сохранять данные в бинарном формате независимо от используемого формата сериализации.

### 4. Отслеживание времени создания

Поле `created_at` позволяет определять время нахождения сообщения в Outbox и анализировать задержки его отправки.

### 5. Асинхронная обработка

Outbox-процессор считывает сохранённые сообщения и отправляет их в брокер. Механизм удаления или подтверждения успешно отправленных сообщений структурой таблицы не фиксируется — определяется реализацией Outbox-процессора.

## Внутреннее представление сообщения: `OutboxMessage`

Класс — внутреннее представление outbox-сообщения в сервисе; поля соответствуют колонкам таблицы. `outbox_partition` в представлении отсутствует — поле в текущей реализации не используется (см. замечания выше).

```csharp
/// <summary>
/// Outbox-сообщение.
/// </summary>
public class OutboxMessage
{
    /// <summary>
    /// Идентификатор сообщения.
    /// </summary>
    public long Id { get; set; }

    /// <summary>
    /// Название топика, в котором будет опубликовано сообщение.
    /// </summary>
    public string Topic { get; set; } = null!;

    /// <summary>
    /// Ключ сообщения.
    /// </summary>
    public byte[] Key { get; set; } = null!;

    /// <summary>
    /// Тело сообщения.
    /// </summary>
    public byte[] Body { get; set; } = null!;

    /// <summary>
    /// Заголовки сообщения.
    /// </summary>
    public string Headers { get; set; } = null!;

    /// <summary>
    /// Номер партиции, в которой будет опубликовано сообщение.
    /// </summary>
    public int? Partition { get; set; }

    /// <summary>
    /// Ключ producer-а.
    /// На основе значения данного свойства определяется
    /// producer (кластер) для публикации сообщения,
    /// сохраненного в outbox.
    /// </summary>
    public string? ProducerKey { get; set; }

    /// <summary>
    /// Дата и время сохранения сообщения в outbox.
    /// </summary>
    public DateTime CreatedAt { get; internal set; }
}
```

## Публикация в Kafka

Обязательный интерфейс-контракт транспорта публикации в проекте **не вводится** (решение владельца): публикация outbox-сообщений выполняется напрямую клиентом Confluent.Kafka (`dependencies.md` §2) из внутреннего представления `OutboxMessage` — без слоя-посредника, который ограничивал бы реализацию (батчинг, delivery-репорты, транзакционный продюсер checkpoint'ов на этапе резервирования). Отправка пакетная и асинхронная, с поддержкой отмены; параметры продюсера (`acks`, идемпотентность, батчинг, таймауты) фиксируются в конфигурации сервиса (план — `implementation-plan.md`, задачи 1 и 4).

### Заголовки

Колонка `headers` публикуется в заголовки Kafka-сообщения: значение разбирается как JSON-объект `{"имя": "строковое значение"}`, каждое свойство становится заголовком (имя — как есть, значение — UTF-8 байты строки). Пустой объект `"{}"` (значение тестового контура Writer) — пустой набор заголовков. Значение, не являющееся JSON-объектом строковых значений (не JSON, не объект, нестроковое значение), — явная ошибка публикации: сообщение не публикуется молча, а задерживается в очереди повторов (см. «Обработка провалов доставки» ниже). Формат фактических значений заголовков (текст, бинарные данные, иное) подлежит проверке при приёмке — напоминание зафиксировано в `implementation-plan.md`, задача 11.

### Обработка провалов доставки

Отправка пакетная: сообщения публикуются пачками до `ProcessorOptions.BatchSize`, в каждый момент в полёте один батч — порядок записи в партицию совпадает с порядком производства. Событие считается опубликованным только после получения подтверждения брокера (delivery-репорт, `acks=all`), а не после вызова отправки.

При провале доставки (delivery-репорт с ошибкой после встроенных повторов librdkafka) сообщение попадает в упорядоченную in-memory очередь повторов и перепроизводится после паузы `RetryDelaySeconds`; новые сообщения не публикуются, пока очередь не опустеет. Заполнение bounded-канала чтения останавливает чтение слота (backpressure), WAL накапливается — потеря исключена, рестарт сервиса не требуется.

Очередь повторов — отдельная структура, а не возврат сообщения в общий канал чтения, по причинам:

- повтор «на месте» по одному сообщению несовместим с батчингом: в полёте до `BatchSize` сообщений, delivery-репорты приходят всей пачкой, провалиться могут несколько сразу; последовательный режим «одно → подтверждение → следующее» лишает батчинга (каждое сообщение платит собственный round-trip до брокера);
- возврат в общий канал нарушает порядок и контракт: канал строго FIFO — проваленное сообщение встанет в хвост и опубликуется после новых (систематическая перестановка «старое после нового»); канал создан с единственным писателем (читателем слота), запись из публикатора нарушила бы контракт и владение завершением; на заполненном ограниченном канале публикатор, будучи единственным читателем, заблокировал бы сам себя; публикация новых продолжалась бы поверх неисправимой ошибки;
- хранение только «последнего сбоя» — тихая потеря при частичном провале батча (провалиться могут несколько сообщений сразу).

Размер очереди повторов естественным образом ограничен объёмом считанного из канала (не больше ёмкости канала плюс размер батча) — отдельной настройки не требует. Локальная перестановка порядка возможна только внутри одного сбойного батча — механика описана в «Порядок доставки» ниже.

### Порядок доставки

- **Без провалов порядок строгий**: батчи обрабатываются строго последовательно (следующий не начинается, пока не решена судьба всех сообщений предыдущего), внутри батча производство идёт по порядку декодирования, идемпотентный продюсер сохраняет порядок и на внутренних повторах librdkafka — порядок записи в партицию совпадает с порядком в WAL.
- **Внутри одного сбойного батча возможна перестановка (out-of-order)**: все сообщения батча производятся до ожидания delivery-репортов, поэтому успешный «младший» m6 может быть записан брокером раньше провалившегося «старшего» m5. Очередь повторов возвращает только провалившиеся (m6 повторно не публикуется), и дренируется первой — m5 перепроизводится раньше новых сообщений, порядок выравнивается со следующего батча. Окно перестановки совпадает с окном at-least-once.
- **`BatchSize = 1` — документированный режим строгой последовательной доставки**: батч из одного сообщения — «отправил → дождался ACK → следующее», порядок строго источниковый, окна перестановки нет вовсе. Цена — каждое сообщение платит собственный round-trip (плюс fsync брокера при `acks=all`), производительность падает с тысяч msg/s до сотен. Включается оператором конфигурацией `CDCOUTBOX__PROCESSOR__BATCHSIZE=1` без изменения кода.

### Подтверждение LSN и checkpoint

Конвейер строго упорядочен: **чтение WAL → отправка в Kafka → ACK → durable checkpoint в `cdc-checkpoints` → подтверждение LSN слота**. Событие считается доставленным после delivery-репорта; позиция слота подтверждается только после того, как checkpoint доставленной позиции подтверждённо сохранён в Kafka. Подтверждение позиции до доставки означало бы потерю сообщений (WAL под подтверждённой позицией перерабатывается, повторить некому) — at-least-once требует именно этого порядка.

- **Граница транзакции.** Ридер буферизует сообщения текущей транзакции до её Commit (pgoutput отдаёт LSN коммита только в Commit-записи) и записывает их в канал пачкой; последнему сообщению проставляется `TransactionEndLsn`. Подтверждать позицию безопасно только после доставки всей транзакции — поэтому штамп стоит только на последнем сообщении, и водяной знак не продвигается «внутри» транзакции. Плата за буферизацию — память ридера в размере одной транзакции источника (батч Writer, ограничен по построению); альтернатива (маркеры границ транзакций в канале) меняла бы контракт канала и обеих сторон конвейера ради той же гарантии.
- **Водяной знак доставки** — наибольший LSN, до которого всё доставлено подряд, без дыр (закладка: двигается только когда всё до неё прочитано). Публикатор продвигает его только при полном успехе батча — максимум `TransactionEndLsn` среди доставленных; при частичном провале знак стоит на месте: доставленные соседи сбойного батча не считаются, а очередь повторов дренируется первой и по порядку, поэтому следующий успешный батч закрывает дыру одним прыжком. Монотонность — знак двигается только вперёд.
- **Сохранение checkpoint.** Внутренний цикл публикатора с каденцией `CheckpointIntervalSeconds` сохраняет водяной знак записью в `cdc-checkpoints`: ключ — имя слота, партиция 0 (однопартичное допущение; общий топик на несколько слотов/сервисов и несколько партиций — задача 15 плана), значение — JSON `{"slotName","lsn","savedAtUtc"}`; продюсер общий с событиями (одна удостоверяющая личность в Kafka). Параметры топика — партиции, replication factor, компакция, `min.insync.replicas` — зафиксированы контрактом `dependencies.md` §1 «Топик `cdc-checkpoints`». Checkpoint считается сохранённым только после ACK записи. Провал сохранения — метрика `outbox_checkpoint_errors_total`, пауза, повтор: публикация событий продолжается, несохранённый прогресс не теряется, при недоступности Kafka конвейер целиком останавливается backpressure'ом (WAL накапливается — норма at-least-once). При graceful stop (завершение канала чтения) выполняется финальное сохранение несохранённого прогресса — рестарт после чистой остановки пере-доставляет ноль сообщений. Транзакционный checkpoint (события + запись одной транзакцией Kafka, fencing через `transactional.id`) — задача 10 плана.
- **Подтверждение слота.** Flush-цикл сессии чтения после каждого сохранённого checkpoint регистрирует позицию `SetReplicationStatus(TransactionEndLsn)` и немедленно выталкивает её серверу `SendStatusUpdate()`. Механика Npgsql: библиотека автоматически отправляет серверу только received-позицию (таймер ~10 с и ответы на keepalive-запросы); flush-позицию — ту, которой сервер двигает `confirmed_flush` логического слота, — регистрирует только явный `SetReplicationStatus`; `SendStatusUpdate` отправляет её немедленно, не дожидаясь таймера. Сбой отправки не фатален — та же позиция уйдёт следующим автоматическим обновлением статуса.
- **Окно дублей рестарта** = доставлено, но ещё не сохранено checkpoint'ом, плюс сохранено, но feedback ещё не дошёл (≤ `CheckpointIntervalSeconds` + round-trip). Рестарт продолжает чтение с `confirmed_flush` и пере-доставляет только это окно (жёсткое прерывание) либо ничего (после graceful stop).
- **Согласование при старте.** Последний checkpoint читается из `cdc-checkpoints` (партиция 0 с начала; компакция хранит по одной записи на ключ — последняя запись ключа и есть текущее значение) **до** какого-либо изменения слота: checkpoint есть + слота нет → явная ошибка, автопересоздание запрещено (новый слот начал бы с текущей позиции WAL — тихая потеря недоставленного окна); checkpoint опережает `confirmed_flush` слота → явная ошибка (состояния сторов разошлись — слот пересоздан/отмотан или checkpoint от другой инсталляции; WAL между позициями мог быть переработан); checkpoint ≤ `confirmed_flush` → продолжение с позиции слота (at-least-once); checkpoint отсутствует → слот создаётся (первый запуск). Сравнение checkpoint с `confirmed_flush` выполняет сервер (`pg_wal_lsn_diff`), разбирая текстовое представление своим парсером pg_lsn: сервис не зависит от формата вывода pg_lsn конкретной реализации PostgreSQL (так, с 18-й версии младшая часть дополняется нулями до восьми цифр — `%X/%08X` вместо `%X/%X`); собственное текстовое представление LSN сервис пишет и читает только сам (`LsnText`, парсер толерантен к ведущим нулям).

## Формат тестового body (контракт Writer ↔ KafkaValidator)

Тестовый контур — генератор нагрузки Writer и валидатор доставки KafkaValidator — договорился о содержимом `body` и `key`. Общего кода между сервисами нет: контракт продублирован в коде каждого сервиса и зафиксирован здесь.

- `body` (bytea, UTF-8 JSON): `{"id": <bigint — id строки>, "runId": "<guid прогона>", "eventType": "TestEvent", "payload": "<строка заданной длины>", "timestamp": "yyyy-MM-ddTHH:mm:ss.fffZ"}`.
- `key` (bytea) = UTF-8 десятичного представления `id`.
- `headers` = `"{}"`; `partition`, `producer_key`, `outbox_partition` Writer не пишет (NULL/DEFAULT).

Идентичность сообщения при валидации — `body.id` (= `id` таблицы; см. «Запись тестовой нагрузки» в `dependencies.md` §3 — Writer резервирует id через `nextval` и вставляет с `OVERRIDING SYSTEM VALUE`). Группировка прогонов — `body.runId`. Дубликаты допустимы (at-least-once); потеря (`written` из Writer, отсутствующий в Kafka) и аномалии (`id` вне ожидаемого набора) фейлят вердикт валидатора.

## Краткое описание для технической документации

Таблица `outbox.messages` предназначена для временного хранения сообщений, подлежащих асинхронной отправке в брокер сообщений.

Каждая запись содержит уникальный идентификатор, топик назначения, ключ, тело сообщения, заголовки, параметры маршрутизации и время создания.

Для распределения нагрузки между экземплярами Outbox-процессора используется поле `outbox_partition`. Поле `partition` позволяет указать целевую партицию брокера сообщений.

Таблица является частью механизма Transactional Outbox, обеспечивающего согласованное сохранение бизнес-данных и сообщений в рамках одной транзакции при соответствующей реализации записи.
