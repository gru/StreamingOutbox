# Streaming Outbox

## Описание

`streaming-outbox` — сервис доставки outbox-сообщений из PostgreSQL в Kafka: чтение из слота логической репликации без polling, запись в Kafka. Доставка at-least-once: позиция слота подтверждается только после подтверждённой записи в Kafka и сохранения durable-checkpoint в служебном топике — потерь нет, дубликаты допустимы. Резервирование Active-Passive: активный экземпляр доставляет, второй ждёт в standby и занимает место при сбое; graceful shutdown завершает доставку финальным checkpoint и подтверждением позиции слота.

## Производительность

Текстовое декодирование значений, батч записи в Kafka — 500 сообщений, размер 256 Б, если не указано иное; активен один экземпляр пары Active-Passive.

### Сценарии

Каждая стадия — прогон Writer'а: запись нагрузки в outbox-таблицу → CDC читает слот и публикует в Kafka → независимый валидатор (консюмер Kafka) сверяет все сообщения прогона (missing/extra/dup); метрики сэмплируются каждые 3 с.

- **Стадия 1 — разогрев:** 100 000 @ 2 000/с (50 с), 256 Б. Выход конвейера на рабочий режим.
- **Стадия 2 — равномерный темп:** 200 000 @ 10 000/с (20 с), 256 Б. CDC идёт в темпе записи, pending ≤ 200.
- **Стадия 3 — стресс-темп:** 400 000 @ 20 000/с (21 с), 256 Б. CDC держит 16–22k/с, отставание не копится.
- **Стадия 4 — безлимитный бурст:** 1 000 000 без rate limit — Writer пишет 47 443/с за 21 с, CDC разбирает образовавшийся бэклог; полный дренаж за 51 с, чистая скорость выборки 25 274/с.
- **Стадия 5 — крупные сообщения:** 200 000 × 4 КБ (846 МБ). CDC в темпе записи — 51–73 МБ/с.

## PostgreSQL и Patroni

### Требования

- PostgreSQL 17 — failover-слоты логической репликации: нативная синхронизация слотов на standby (slotsync worker) появилась в 17, раньше слоты не переживают promotion.
- Кластер под управлением Patroni (DCS — etcd); сервис подключается через HAProxy к текущему primary.
- Плагин `pgoutput` (встроенный), протокол v1.

### Настройки PostgreSQL

| Параметр                                    | Значение  | Зачем                                                                                      |
|---------------------------------------------|-----------|--------------------------------------------------------------------------------------------|
| `wal_level`                                 | `logical` | логическая репликация; нужен на всех нодах, включая standby — иначе slotsync worker падает |
| `sync_replication_slots`                    | `on`      | синхронизация failover-слотов на standby                                                   |
| `hot_standby_feedback`                      | `on`      | обязательна для синхронизации слотов                                                       |
| `max_replication_slots` / `max_wal_senders` | ≥ 10      | запас слотов и walsender'ов (физические реплики + failover-слоты)                          |
| `max_slot_wal_keep_size`                    | `-1`      | WAL не отбрасывается: слот удерживает его до подтверждения доставки                        |

### Настройки Patroni

- `synchronous_mode: true` (`strict: false`) — синхронная физическая репликация; без strict кластер остаётся доступным на запись при отсутствии sync-standby.
- `synchronized_standby_slots` на primary пересобирается после каждой смены лидера (из активных физических слотов) — иначе логический декодинг нового primary блокируется ожиданием стендбая.

### Таблица outbox

```sql
CREATE SCHEMA IF NOT EXISTS outbox;

CREATE TABLE IF NOT EXISTS outbox.messages (
  id               bigint       GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  topic            varchar(255) NOT NULL,
  key              bytea        NOT NULL,
  body             bytea        NOT NULL,
  headers          varchar      NOT NULL,
  partition        integer,
  producer_key     varchar(255),
  created_at       timestamptz  NOT NULL DEFAULT now(),
  outbox_partition integer      NOT NULL DEFAULT 0
);
```

### Publication

```sql
CREATE PUBLICATION outbox_publication
  FOR TABLE outbox.messages
  WITH (publish = 'insert');
```

- `publish = 'insert'`: сообщение появляется в таблице одной вставкой — доставка строится на INSERT; очистка строк (DELETE) из эмиссии исключена, слот несёт один change на сообщение.
- Создаёт инициализация/миграции, а не сервис: `CREATE PUBLICATION` требует `CREATE` на БД и владения таблицей — у роли сервиса таких прав нет.

### Слот создаёт сервис

Failover-слот (`pgoutput`, `failover => true`) сервис создаёт сам при первом старте идемпотентно так как позиция слота — состояние доставки, и его жизненный цикл согласован с checkpoint-стором.

### Права пользователя outbox-сервиса

```sql
CREATE ROLE sys_replication LOGIN
  NOSUPERUSER NOCREATEDB NOCREATEROLE REPLICATION NOINHERIT
  PASSWORD '...';

GRANT CONNECT ON DATABASE outbox TO sys_replication;
GRANT USAGE ON SCHEMA outbox TO sys_replication;
```

`SELECT` на таблицу не требуется: стриминг pgoutput читает сообщения через слот, а не SQL-запросом. `SUPERUSER` не нужен.

## Kafka

Сервис использует Kafka-транзакции: батч событий и checkpoint фиксируются одним commit, а постоянный `transactional.id` продюсера даёт fencing лидера в паре Active-Passive. Отдельные настройки брокера не требуются при любой топологии кластера — внутренний топик транзакций `__transaction_state` создаётся брокерами при первом старте продюсера;

Сервис не создаёт топики автоматически — их создаёт инфраструктура.

### Служебный топик `cdc-checkpoints`

Durable-checkpoint — подтверждённая позиция доставки (LSN): сервис сохраняет её в `cdc-checkpoints` после подтверждённой записи батча в Kafka и лишь затем подтверждает позицию слота. Checkpoint пишется одной транзакцией с батчем событий и считается сохранённым после её commit. На этом же топике арбитраж пары Active-Passive: контрольная consumer group, владение единственной партицией = лидерство.

### Рекомендованные параметры топика

| Параметр         | Значение  | Зачем                                                                          |
|------------------|-----------|--------------------------------------------------------------------------------|
| `partitions`     | 1         | ОБЯЗАТЕЛЬНО. Одна партиция = один лидер контрольной группы (модель арбитража); |
| `cleanup.policy` | `compact` | РЕКОМЕНДУЕТСЯ.                                                                 |

## Резервирование и Active-Passive

Пара экземпляров сервиса: один активный — читает слот и публикует в Kafka, второй ждёт в standby и занимает место при сбое. Арбитраж — Kafka Consumer Group на служебном топике `cdc-checkpoints`, защита от устаревшего лидера — fencing транзакционного продюсера.

### Выбор лидера

- Контрольная consumer group `cdc-outbox-<slot>` (выводится из имени слота, одна на слот) подписана на единственную партицию `cdc-checkpoints`: назначение партиции экземпляру = лидерство.
- Standby держит членство группы регулярным poll'ом и ничего не делает: не читает слот, не пишет в Kafka. Оба экземпляра всегда живы и здоровы — готовность ≠ лидерство.

### Переключение

- Внезапная смерть лидера: группа обнаруживает потерю по истечении session timeout (~`session.timeout.ms`) → rebalance → партиция назначается standby → он становится активным.
- Graceful stop лидера: LeaveGroup — партиция переходит резервному сразу, без ожидания таймаута.
- Новый лидер выполняет стартовые проверки, читает последний checkpoint из `cdc-checkpoints` и продолжает доставку с позиции слота; окно между checkpoint и подтверждением пере-доставится (at-least-once).

### Fencing

- Транзакционный продюсер с постоянным `transactional.id = cdc-outbox-<slot>`: инициализация нового лидера отбрасывает незавершённые транзакции устаревшего — тот не может ни зафиксировать батч, ни откатить checkpoint назад. Получив fencing-ошибку, прежний лидер останавливает доставку и уходит в standby.
- Эксклюзивность слота — последняя линия защиты: два одновременных читателя одного слота невозможны.
