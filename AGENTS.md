# AGENTS.md

Проект `streaming-outbox`: сервис, читающий outbox-сообщения из PostgreSQL 17 через слот логической репликации (плагин pgoutput, Npgsql Logical Replication API — стриминговая репликация, без polling) и публикующий их в Kafka через Confluent.Kafka.

## Главное правило

**При реализации сервиса опираться на `docs/dependencies.md`, `docs/recommendations.md`, `docs/metrics.md` и `docs/outbox-table.md`.**

`docs/dependencies.md` — единый источник правды о:

- версиях инфраструктуры (PostgreSQL, Patroni, etcd, HAProxy, Kafka, observability-стек);
- версиях NuGet-зависимостей сервиса (Npgsql, Confluent.Kafka, OpenTelemetry);
- формате outbox-таблицы `outbox.messages` (DDL);
- канонических примерах создания publication и failover-слота репликации.

`docs/recommendations.md` — архитектурные требования к реализации CDC-сервиса:

- управление replication slot (создаётся сервисом при первом запуске, идемпотентно) и устойчивые checkpoint'ы;
- конвейер `WAL Read → Kafka Send → Kafka ACK → Durable Checkpoint → LSN Flush` — ни checkpoint, ни LSN не опережают подтверждённую Kafka-доставку;
- at-least-once доставка (дедупликация — Inbox потребителя), backpressure на ограниченных очередях, конфигурируемые пачки/in-flight;
- восстановление после сбоев, монотонность подтверждаемой позиции, явные ошибки вместо тихих пропусков;
- Checkpoint Store — отдельный Kafka topic с log compaction (ключ — имя replication slot), Recovery Mode для ручного аварийного восстановления;
- балансировка экземпляров Active-Passive через Kafka Consumer Group (служебный topic `cdc-checkpoints`, ровно одна партиция — контракт заморожен решением владельца 2026-11-06): partition группы определяет активного (группа — одна на слот: `cdc-outbox-<slot>`, реализована задачей 15; слоты общего топика выборами не мешают друг другу), transactional producer (постоянный `transactional.id` от слота) блокирует устаревших лидеров, эксклюзивность слота — последняя линия защиты;
- контроль простоя потока: при отсутствии новых событий дольше `idle_timeout` сервис пишет WARN в лог, не останавливаясь (drain-режим исключён решением владельца); порядок обновления PostgreSQL (pg_upgrade ≥17 переносит слоты с новыми LSN, dump/restore — нет; перед миграцией — дождаться доставки по idle-предупреждениям, после — согласование checkpoint через `recovery_mode`).

`docs/metrics.md` — обязательные метрики сервиса (prometheus-net, класс `OutboxMetrics`; единый label `slot` = имя replication slot у всех метрик, критерий нейминга `outbox_<подсистема>_<показатель>`): активность и итерации процессора, отправленные/прочитанные/сохранённые сообщения, ошибки, возраст сообщений (`outbox_message_age_seconds`), латентность публикации, in-flight события, checkpoint-стор (age/lag/ошибки), переподключения к слоту и переключения активного экземпляра; сводная таблица и приоритетные показатели мониторинга.

`docs/outbox-table.md` — описание таблицы `outbox.messages`: назначение (Transactional Outbox), структура полей, партиционирование (`partition` брокера / `outbox_partition` процессора), контракты сервиса (`OutboxMessage`, настройки `OutboxStorageOptions` — схема/таблица; публикация в Kafka — напрямую Confluent.Kafka без интерфейса-транспорта), связь с метриками.

`docs/implementation-plan.md` — план реализации outbox-сервиса из небольших задач с проверяемым результатом (конвейер → устойчивость → режимы → резервирование → приёмка); чек-лист прогресса в начале файла, каждая задача завершается живой проверкой на стенде.

`docs/writer.md` — особенности реализации Writer (запись батча, ретраи и неоднозначный commit, диспетчер, подключения, формат тестового сообщения, метрики): комментарии в коде Writer сознательно минимальны, пояснения по реализации живут здесь.

Любое изменение версии, схемы или архитектурного решения **сначала** фиксируется в этих файлах, **затем** в коде и инфраструктуре.

Ключевые правила стенда (подробности и проверки — `docs/stand.md`):

- **Управление стендом — `scripts/stand.sh`**: `up [--build] | down | wipe | bootstrap | status | check | primary | restart | rebuild | logs`, инъекции отказов `fail pg|pgN|pg-all|kafkaN|kafka-all|haproxy|outbox-1|outbox-2|outbox-all` + `restore [target]` (target `outbox-N` стартует `cdc-outbox-N`; outbox-2 — только при включённом профиле `redundancy`, операции с ним идут с флагом `--profile redundancy` — без него compose сервис «не видит»), `switchover [candidate]`, тестовый контур `load <total> [size] [rate]` + `verdict [runId]`. `check` — полный health-check (59 проверок базово — контейнер и /health только cdc-outbox-1, failover-слот outbox_slot создаёт сервис, 9 таргетов Prometheus; с профилем redundancy — 62 и 10, ветки cdc-outbox-2 условные); после смены топологии PG команды сами прогоняют bootstrap и settle-ожидания (первая проба Writer /ready после demote даёт разовую 503 на мёртвом коннекте пула; залипающий postgres-exporter рестартуется автоматически). Приёмочные харнессы — `scripts/test/integration-delivery.sh` (доставка end-to-end + отказы; фаза Active-Passive включается автоматически при поднятой паре) и `scripts/test/upgrade-rehearsal.sh` (репетиция dump/restore-обновления PG; разрушительная для БД outbox — запускать отдельно) — раздел docs/stand.md «Приёмочные харнессы».

- **Контейнерные прогоны НЕ пишут в папку репозитория** (`scripts/test.sh`/`scripts/lint.sh` монтируют репо read-only и работают с копией исходников внутри одноразового контейнера; `obj/bin` остаются только внутри контейнера): запись `obj/` из linux-контейнера поверх артефактов IDE (SDK хоста другой, кэш NuGet хоста при этом не задейств — контейнеры без `~/.nuget`) плюс ненадёжная доставка файловых событий из контейнера через VirtioFS (Docker Desktop) ломали file-watcher IDE — «пропадали все типы» до пересборки решения (грабля найдена и устранена 2026-11-01). - **После каждой смены primary — `scripts/init/apply-bootstrap.sh`** (обновляет `synchronized_standby_slots` на новом лидере).
- **Сброс позиции слота / восстановление после утраты слота — Recovery Mode (задача 7)**: drop слота при живом checkpoint валит старт явной ошибкой «автопересоздание запрещено» (штатная защита — пересоздание с текущей позиции потеряло бы недоставленное окно; лечится именно recovery). Сброс/восстановление: stop cdc-outbox-1 → `pg_drop_replication_slot('outbox_slot')` на лидере → `CDCOUTBOX__RECOVERYMODE=true docker compose up -d --no-deps cdc-outbox-1` (слот пересоздаётся с текущей позиции WAL, checkpoint переписывается **до** начала чтения, WARN «Recovery Mode: checkpoint X → Y»; события между позициями пропускаются осознанно) → рестарт без флага. - **Writer и KafkaValidator — самостоятельные проекты: общего кода с outbox-сервисом и между собой НЕ имеют.** Контракт тестового body/key зафиксирован в `docs/outbox-table.md` и сознательно продублирован в коде обоих сервисов.
- Writer: INSERT+DELETE одной транзакцией (таблица всегда пустая); id — `bigint` identity, резервируется `nextval` ДО сборки body и вставляется с `OVERRIDING SYSTEM VALUE` (детали и гранты sys_writer — `docs/dependencies.md` §3, «Запись тестовой нагрузки»); повтор батча теми же id → `unique_violation` = детект AlreadyCommitted.
- KafkaValidator: идентичность сообщения — `body.id` (= id строки, `long`), группировка — `body.runId`; консюмер — сырой Confluent.Kafka (`ValidatorConsumerService`: группа `kafka-validator`, Earliest, оффсеты никогда не коммитятся — каждый старт перематывает topic с начала и восстанавливает счётчики прогонов; KafkaFlow 3.0.10 удалён 2026-10-27 — дефект связки с Confluent 2.3.0: партиции назначаются, записи не доставляются, воспроизведено минимальным пробником — `docs/dependencies.md` §2 «Отказ от KafkaFlow»); обогащение снапшотом CDC не реализовано (`verdict.Cdc` всегда null — поле сохранено под будущее обогащение).
- Метрики обоих сервисов — prometheus-net 5.0 (`Metrics.Create*`, `MapMetrics`), без OTel; OTel-пины 1.11 в CdcOutbox.Host — задел под задачу 16 плана (трассировка activity/span + runtime-метрики, решение владельца 2026-11-04). Грабли: внутри namespace `*.Metrics` имя `Metrics` резолвится в namespace — квалифицировать `Prometheus.Metrics`; `UseMetrics` в 5.0 нет — достаточно `MapMetrics`; labels — `WithLabels(...).Inc(...)`.

- Код и тесты проверяются на соответствие `.editorconfig` (корень репозитория): **после любого изменения `.cs`/`.csproj` запускать `scripts/lint.sh`** (обёртка над `dotnet format StreamingOutbox.sln --verify-no-changes` в контейнере `mcr.microsoft.com/dotnet/sdk:8.0`). Линт должен быть зелёным так же, как сборка и тесты, — до завершения работы. Авто-фикс нарушений: `dotnet format StreamingOutbox.sln` без `--verify-no-changes` (правки пересматривать по диффу).
- **Строгая сборка — `Directory.Build.props`** (применяется ко всем проектам): `TreatWarningsAsErrors`, `EnableNETAnalyzers` + `AnalysisLevel=preview`, `EnforceCodeStyleInBuild` — правила .editorconfig уровня warning/error блокируют и сборку (проверено на SDK 8.0: CS0219-warning валит сборку; IDE0161 из .editorconfig валит сборку). **IDE0005 (неиспользуемые using'и) блокирует и сборку, и dotnet format** (проверено 2026-10-22 негативным тестом; раньше молча пропускался из-за опечатки в ключе .editorconfig — `dotnet_diagnostic.IDE0005_severity` с подчёркиванием вместо точки игнорируется целиком).
- Блокирующие правила (severity warning/error в .editorconfig): форматирование (4 пробела, LF, UTF-8, финальный перевод строки, без хвостовых пробелов), file-scoped namespaces, using вне namespace + System-группой первой, без `this.`, явные модификаторы доступа, скобки у многострочных `if` (`when_multiline`), нейминг (типы/методы/свойства PascalCase, интерфейсы `IPascalCase`, private instance-поля `_camelCase`, `const`/`static` — PascalCase, параметры/локальные camelCase), readonly-поля, где возможно, авто-свойства, target-typed `new()`, неиспользуемые using'и (IDE0005 — для его корректной работы в csproj включён `GenerateDocumentationFile` + `NoWarn CS1591`).
- **Порядок членов класса — единый для всех классов** (2026-11-06): StyleCop.Analyzers (пакет в `Directory.Build.props`, `PrivateAssets=all`) полностью выключен по категориям в `.editorconfig`, точечно включены только правила порядка членов (severity warning — блокируют и линт, и сборку): SA1201 — по виду (поля → конструкторы → финализаторы → delegates/events/enums/interfaces → свойства → индексаторы → операторы → методы, вложенные типы последними); SA1203 — const-поля выше не-const; SA1214 — readonly выше не-readonly; SA1202 — по доступности в пределах вида (public → internal → … → private); SA1212/SA1213 — аксессоры get до set, add до remove; SA1206 — ключевые слова объявления (доступность → static → прочие). Сознательно исключены: SA1204 (static строго до instance) — конфликтует с раскладкой тест-классов «сначала тесты, затем private-хелперы»; правила порядка using (SA1200/SA1208-SA1211/SA1216/SA1217) — using уже управляются секцией IDE0055. SA1201 упорядочивает и верхнеуровневые типы файла: delegates и enums — до классов (проверено делегат-пробой 2026-11-06).
- **Один класс на файл — SA1402** (2026-11-06, решение владельца; закрыл pending-исключения «по одному типу на файл» из docs/writer.md «Устройство файлов и видимость»): точечно включён severity warning (категория MaintainabilityRules выключена, ID перекрывает) — в файле максимум один класс, record считается классом; enum и delegate рядом с единственным классом допустимы (дефолт SA1402 — учитываются только классы, struct/interface рядом с классом дефолт тоже допускает, в кодовой базе таких файлов нет); частичные и file-local типы не затрагиваются. Ради правила 7 файлов разделены — `LoadProfile`/`BatchResult`/`GeneratedMessage`/`RecoveryDecision`/`OutboxColumnPlan`/`PublicationState`/`ConsumedMessage` в собственных файлах (те же каталоги и namespace, тесты не менялись); enum'ы `BatchOutcome`/`RecoveryAction`/`OutboxColumnSlot` остались при своих классах как допустимые. Проверено 2026-11-06 негативным тестом: до разделения линт падал с SA1402 ровно на 7 файлах; после — зелёный при живых enum+class файлах и class+delegate пробе.
- Спорные предпочтения (var, expression-bodied и пр.) зафиксированы в .editorconfig на уровне suggestion — линт их не блокирует.
- XML-doc комментарии — только в многострочном виде: `/// <summary>`, текст и `/// </summary>` на отдельных строках. Ссылки на файлы документации (`docs/*.md`) в коде outbox-сервиса (`CdcOutbox.*`) не используются — ни в runtime-строках, ни в комментариях (решение владельца 2026-11-04; для Writer/KafkaValidator непринципиально — исторические ссылки там остались).
- **Содержание комментариев — короткое «что это», без деталей реализации** (решение владельца 2026-11-07): `<summary>` — одна короткая фраза о том, чем является сущность или настройка. Без механики работы, обоснований «почему так», перечислений режимов и источников, ссылок на параметры драйверов (`ProducerConfig LingerMs` и т.п.); единицы измерения (мс/с/байт) — часть смысла и остаются. То же касается inline-комментариев: «что», не «как». Пояснения по реализации и мотивация — в `docs/*.md`, не в коде. Эталон — `src/CdcOutbox.Core/Configuration/` (вычищен 2026-11-07): «Таймаут доставки сообщения, включая ретраи, мс.», «Название служебного topic checkpoint-стора.». Summary `LeadershipArbiter` приведён к правилу 2026-11-07; остальной код src/ ещё не вычищен.
- **Календарное время — строго через `TimeProvider`** (решение владельца): никаких прямых `DateTime.UtcNow`/`DateTimeOffset.UtcNow` в коде src — каденции, дедлайны, паузы и «возрасты» берутся только у инжектируемого `TimeProvider` (в сервисе — DI-синглтон `TimeProvider.System`), иначе логика времени не проверяется фейковыми часами в тестах. Calendar-сентинелы («никогда» = `DateTimeOffset.MinValue`) запрещены — «никогда» выражается `null`. Измерение коротких интервалов (латентность публикации) — `Stopwatch.GetTimestamp()`: это не календарное время. Тестовый контур может использовать реальные часы.

## Рефакторинги через Rider MCP

JetBrains Rider (MCP) подключён к этому solution — рефакторинги исходного кода доступны как инструменты:

- **Переименование — да**: `rename_refactoring` (контекстно-зависимое, обновляет ВСЕ ссылки на символ по всему solution — не текстовая замена). Переименование public API/типов делать через него, а не replace'ом.
- **Удаление — отдельной рефакторинг-операции нет** (safe delete отсутствует): файлы/символы удаляются обычными средствами (Edit/`git rm`) с обязательной проверкой остаточных ссылок (`search_in_files_by_text`) и прогоном lint+test.
- Сопутствующее: `get_symbol_info` (декларация/семантика символа), `get_file_problems` (инспекции IDE по файлу), `search_in_files_by_text`/`_by_regex`, `reformat_file`, `build_project`. Канонические сборка/линт/тесты — по-прежнему только контейнером через `scripts/*.sh` (локальный SDK не 8.й); инструменты Rider — для навигации, инспекций и рефакторингов, не для замены прогона.

## Ключевые ограничения

- Чтение outbox — только через logical replication slot; SELECT-polling таблицы запрещён.
- Механика CDC — outbox-таблица + pgoutput (pgoutput не передаёт logical messages ни в одной версии PostgreSQL — доставка строится на INSERT).
- Подтверждение LSN слота — только после Kafka delivery (`acks=all`): семантика at-least-once, дубликаты допустимы, потери нет.
- Kafka-клиент всего решения — Confluent.Kafka напрямую: outbox-сервис (идемпотентный продюсер событий `acks=all`, транзакционный продюсер checkpoint'ов `cdc-checkpoints` (fencing лидера) и консюмер control-группы — реализованы задачами 5/10) и консюмер валидатора. KafkaFlow исключён полностью. Из outbox-сервиса — решением владельца 2026-10-22 (нет доступа к Kafka-транзакциям ни в одной линии — [Farfetch/kafkaflow#566](https://github.com/Farfetch/kafkaflow/issues/566) открыт с 2024-04 без реакции мейнтейнеров, проверено рефлексией 3.0.10; полная причина — `docs/dependencies.md` §2). Из валидатора — решением владельца 2026-10-27: дефект связки KafkaFlow 3.0.10 + Confluent.Kafka 2.3.0 (консюмер назначал партиции и не доставлял ни одной записи; воспроизведено минимальным пробником на чистом KafkaFlow, сырой Confluent с той же конфигурацией работает).
- .NET 8 (`net8.0`) и PostgreSQL 17 — строго; всё в Docker Compose.
- Комментарии в коде (включая XML-doc) — только с разрешения владельца; пояснения по реализации живут в `docs/*.md` (стиль Writer — `docs/writer.md`).
