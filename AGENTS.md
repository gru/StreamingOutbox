# AGENTS.md

Проект `streaming-outbox`: сервис, читающий outbox-сообщения из PostgreSQL 17 через слот логической репликации (плагин pgoutput, Npgsql Logical Replication API — стриминговая репликация, без polling) и публикующий их в Kafka через Confluent.Kafka.

## Главное правило

**При реализации сервиса опираться на `README.md` и корневые файлы документации, на которые он ссылается (`CONFIGURATION.md`, `METRICS.md`, `REVIEW.md`, `STRUCTURE.md`, `REQUIREMENTS.md`), и на раздел «Версии и контракты» этого файла.**

- `README.md` — требования к PostgreSQL/Patroni и Kafka (DDL outbox-таблицы, publication, права, настройки, топик `cdc-checkpoints`), конвейер доставки и гарантии (at-least-once, retry-очередь, порядок, backpressure), резервирование Active-Passive и fencing, Recovery Mode.
- `CONFIGURATION.md` — все ключи конфигурации `CdcOutbox:*` (обязательность, дефолты, рекомендации) и вычисляемые/зафиксированные параметры Kafka-клиентов.
- `METRICS.md` — обязательные метрики (класс `OutboxMetrics`; единый label `slot` = имя replication slot у всех метрик, критерий нейминга `outbox_<подсистема>_<показатель>`, приоритетные показатели мониторинга).
- `REVIEW.md` — карта чтения кода по потоку управления и данных (точка входа → лидерство → конвейер → публикация → жизненный цикл старта).
- `STRUCTURE.md` — проекты решения, каталоги, скрипты и харнессы, стенд (состав, порты, правила, Recovery Mode на стенде, объекты БД и роли).
- `REQUIREMENTS.md` — исходные требования (14 пунктов) и таблица отступлений с причинами и датами решений владельца.
- Раздел «Версии и контракты» этого файла (ниже) — версии инфраструктуры и NuGet-зависимостей, контракт с Kafka-окружением и права принципала (ACL), контракты данных (бинарный формат pgoutput, заголовки, тестовое тело Writer↔KafkaValidator), согласование checkpoint со слотом при старте, условия корректности failover-слота, порядок обновления PostgreSQL, незавершённые задачи (13/14/16/17).

Любое изменение версии, схемы или архитектурного решения **сначала** фиксируется в этих файлах (версии и контракты — в разделе «Версии и контракты» этого файла), **затем** в коде и инфраструктуре.

### 3. Контракт с Kafka-окружением

Сервис рассчитан на произвольное Kafka-окружение: параметры окружения — вход, параметры клиентов выводятся из них (таблица производных — CONFIGURATION.md «Вычисляемые и зафиксированные параметры Kafka»). Провижининг топиков (RF, `min.insync.replicas`, `cleanup.policy`, партиции, лимиты размеров) код не проверяет — только существование топиков и классификацию ошибок протокола.

Предусловия окружения:

| Параметр окружения | Условие |
|---|---|
| `group.min/max.session.timeout.ms` | допускать `SessionTimeoutMs` (наш 15 с) — иначе JoinGroup падает `INVALID_SESSION_TIMEOUT` |
| `transaction.max.timeout.ms` | ≥ `DeliveryTimeoutMs + 60 000` (наш `TransactionTimeoutMs` 180 000) — иначе `InitTransactions` падает |
| `message.max.bytes` (брокер) и `max.message.bytes` топиков | ≥ `MessageMaxBytes` (1 000 000) — иначе крупные записи вечно ретраятся |
| `transaction.state.log.replication.factor` / `.min.isr` | `__transaction_state` создаётся брокерами при первом `InitTransactions`; на 1-брокерном кластере RF=1/minISR=1 (так настроен `kafka-it`) |
| Топики `cdc-checkpoints` (1 партиция, compact), `outbox.events` | существуют; рекомендуются RF ≥ 2, minISR ≥ 2 |
| Grace-период развёртывания (`stop_grace_period` / `terminationGracePeriodSeconds`) | > `ShutdownTimeoutSeconds` (30 с) — иначе SIGKILL обрежет финальный checkpoint |

Права принципала при включённой авторизации (в стенде авторизации нет; провижининг-параметры кодом не проверяются):

| Ресурс | Операции | Зачем |
|---|---|---|
| `TRANSACTIONAL_ID` `cdc-outbox-<slot>` | WRITE + DESCRIBE | транзакционный продюсер: `InitProducerId` (акт fencing) / `FindCoordinator` |
| `GROUP` `cdc-outbox-<slot>` | READ (+ DESCRIBE) | контроль-консюмер арбитража |
| `TOPIC` `cdc-checkpoints` | WRITE + DESCRIBE + READ | checkpoint-записи; READ — арбитр (членство группы) и чтец `ReadLatest` |
| `TOPIC` `outbox.events` | WRITE + DESCRIBE | продюсер событий |
| `CLUSTER`, `__transaction_state` | — | права не требуются: внутренний топик трогают только брокеры |

### 4. Контракты данных

#### Бинарный формат значений pgoutput

Включение — `CdcOutbox:Replication:Binary` (опция `binary 'true'` в START_REPLICATION, PostgreSQL 14+): значения колонок приходят бинарным представлением типа (главный выигрыш — `bytea` идёт сырыми байтами без hex-надбавки). Сырые байты читаются `GetStream()` (минуя конвертер типа Npgsql) и декодируются по OID колонки из плана колонок:

| Тип колонки | OID | Представление |
|---|---|---|
| `bigint` (id) | 20 | int64, big-endian |
| `integer` (partition) | 23 | int32, big-endian |
| `bytea` (key, body) | 17 | сырые байты (без hex-обрамления) |
| `varchar` (topic, headers, producer_key) | 1043 | UTF-8 |
| `timestamptz` (created_at) | 1184 | int64 микросекунд от 2000-01-01 00:00:00 UTC (отрицательные — моменты до эпохи) |

OID вне контракта или несовпадающий вид значения — явная ошибка декодирования с именем колонки (транзиентная: чтение повторится с той же позиции, WAL не теряется). NULL обрабатывается одинаково для обоих форматов. Переключение настройки между рестартами безопасно: позиция слота и checkpoint от формата не зависят.

#### Заголовки

Колонка `headers` — JSON-объект `{"имя": "строковое значение"}`; публикуется в заголовки Kafka-сообщения (имя — как есть, значение — UTF-8 байты строки):

- значения — только строки: нестроковые JSON-значения (числа, `true`/`false`, `null`, вложенные объекты/массивы) — ошибка формата, сообщение не публикуется и не пропускается, а удерживается в очереди повторов;
- бинарные данные не поддерживаются (колонка `varchar`; кодируются пишущим внутри строкового значения, например base64);
- повторяющееся имя свойства — после разбора действует последнее значение;
- пустой объект `"{}"` — пустой набор заголовков.

#### Тестовое тело (контракт Writer ↔ KafkaValidator)

body — UTF-8 JSON `{"id","runId","eventType":"TestEvent","payload","timestamp"}` (timestamp — UTC с миллисекундами, `yyyy-MM-ddTHH:mm:ss.fffZ`); key — UTF-8 десятичного id; headers — `"{}"`; `partition`/`producer_key`/`outbox_partition` не пишутся. Идентичность сообщения при валидации — `body.id`, группировка прогонов — `runId`; дубли допустимы (at-least-once), потеря и аномалии валят вердикт (pass ⇔ missing=0 && unexpected=0). Консюмер валидатора: группа `kafka-validator`, `AutoOffsetReset=Earliest`, офсеты никогда не коммитятся — каждый старт перематывает topic с начала.

### 5. Согласование checkpoint со слотом при старте

Инвариант: checkpoint фиксируется одной транзакцией с доставкой, позиция слота подтверждается только после подтверждённого commit checkpoint — закоммиченный checkpoint на позиции Y доказывает доставку всего до Y.

| Состояние на старте | Действие |
|---|---|
| checkpoint отсутствует | продолжение (первый запуск / пересоздание checkpoint-топика) |
| checkpoint == `confirmed_flush` | штатное продолжение с позиции слота |
| checkpoint опережает `confirmed_flush`, слот жив | WARN + продолжение с позиции слота: данные до checkpoint уже доставлены, окно пере-доставится дублями; если WAL у позиции слота переработан — сервер сам откажет в чтении терминальной ошибкой |
| `confirmed_flush` опережает checkpoint | принять `confirmed_flush` слота как checkpoint (durable до начала чтения) + WARN + `outbox_checkpoint_skips_total` (решение владельца 2026-11-09): окно между позициями пропускается, его доставка недоказуема — состояние недостижимо штатной работой сервиса (только внешние действия), читать назад от позиции слота невозможно в любом случае; терминальной ошибкой не является, остановка сервиса отклонена |
| слот отсутствует, checkpoint жив | терминальная ошибка: автопересоздание запрещено (новый слот начал бы с текущей позиции WAL и молча пропустил бы недоставленное окно); восстановление — Recovery Mode |
| `confirmed_flush` пуст | терминальная ошибка: слот непригоден, автодроп существующего слота запрещён |
| Recovery Mode, слот отсутствует | создать слот с текущей позиции WAL, принять её как новый checkpoint (сохранить durable до начала чтения; окно между позициями пропускается осознанно) |
| Recovery Mode, checkpoint опережает `confirmed_flush` | принять `confirmed_flush` слота как новый checkpoint |
| Recovery Mode, `confirmed_flush` опережает checkpoint | no-op (рассогласования нет): продолжение и так с позиции слота; расширение Recovery Mode на это состояние отклонено (2026-11-09) |

Сравнение checkpoint с `confirmed_flush` выполняет сервер (`pg_wal_lsn_diff`): сервис не зависит от формата вывода pg_lsn (PG ≤17 `%X/%X`, PG 18+ `%X/%08X`); собственное текстовое представление LSN (`LsnText`) сервис пишет и читает только сам.

Отказ от остановки при опережении `confirmed_flush` (решение владельца 2026-11-09): окно между позициями физически нечитаемо — сделать уже ничего нельзя независимо от того, стоит сервис или читает; остановка в информационных целях создавала бы устранимую аварию (доставка простаивала бы при доказанно нечитаемом окне). Вместо остановки — durable-принятие позиции слота как checkpoint + WARN + `outbox_checkpoint_skips_total` (видимость без потери доступности); Recovery Mode на это состояние не расширяется — при включённом флаге no-op.

### 6. Failover-слот: условия корректности

Слот создаёт сам сервис идемпотентно: `pg_create_logical_replication_slot(slot_name => 'outbox_slot', plugin => 'pgoutput', failover => true)` — достаточно атрибута REPLICATION роли.

- `failover => true` включает нативную синхронизацию слота на standby (PG17 slotsync worker); на стендбаях нужны `sync_replication_slots = on` и `hot_standby_feedback = on`.
- Слот — объект прикладной БД: slotsync синхронизирует слоты только БД из `dbname` в `primary_conninfo` стендбая (в Patroni — опция `postgresql.database`).
- `synchronized_standby_slots` на primary принимает только физические слоты и собирается из **активных**: слот мёртвого стендбая остаётся в каталоге, но его включение в список блокирует логический декодинг primary (walsender failover-слота виснет в catchup до возврата стендбая); пересбор после каждой смены primary (`ALTER SYSTEM` + `pg_reload_conf()`; на стенде — `scripts/init/apply-bootstrap.sh`).
- Создание слота — только на primary: в PG17 вызов на standby не завершается (сессия виснет, слот при этом виден другим сессиям existing+active) — сервис перед созданием явно проверяет `pg_is_in_recovery()`.
- Существующий слот без failover принимается с WARN (failover — инфраструктурное решение о переживании promotion, чтению флаг не требуется).
- Непотребляемый слот со временем перестаёт синхронизироваться (catalog_xmin стендбая обогнал слот) и при promotion не сохраняется — до появления потребителя продвигать слот вручную; сервис делает это сам после Kafka delivery.

### 7. Порядок обновления PostgreSQL

LSN не непрерывны между старым и новым кластером: pg_upgrade с PostgreSQL ≥17 может перенести логические слоты (с новыми LSN), pg_upgrade со старых версий и dump/restore слоты не переносят.

1. Остановить бизнес-приложение / запретить создание новых outbox-событий.
2. Дождаться доставки накопленного: `outbox_checkpoint_lag_bytes` → 0, в логе — idle-предупреждения об отсутствии новых событий.
3. Остановить экземпляры CDC (graceful stop сохраняет подтверждённый прогресс).
4. Выполнить pg_upgrade или dump/restore.
5. Запустить CDC в Recovery Mode — согласовать checkpoint с новой позицией слота или создать отсутствующий слот.
6. После сохранения нового checkpoint и начала чтения вернуть CDC в обычный режим и возобновить запись.

Репетиция пути dump/restore — `scripts/test/upgrade-rehearsal.sh`.

### 8. Незавершённые задачи

Задачи 1–12 и 15 плана реализации выполнены (хроника живых проверок — git-история и `testruns/`); остались:

- **13 — политика для неисправимых ошибок данных (битые `headers`).** Сейчас битое `headers` (не JSON-объект строк) удерживается в очереди повторов: ERROR + `errors_total`, чтение останавливается backpressure'ом, WAL копится — ни потери, ни тихого пропуска. Решить судьбу: пропуск с явным аудитом / dead-letter topic / остановка до оператора (влияние на вердикты валидатора — пропуск должен быть виден).
- **14 — старт с ограниченными правами в Kafka.** `CheckpointTopicVerifier` запрашивает метаданные всех топиков (`IAdminClient.GetMetadata` без аргументов) — при принципале с ограниченными правами брокер отвечает `TOPIC_AUTHORIZATION_FAILED`, подъём хоста валится. Нужны адресные запросы метаданных по имени топика; минимальные права — таблица ACL выше.
- **16 — OTel: трассировка и runtime-метрики.** Activity/span конвейера (чтение слота → декодирование → публикация → ACK → checkpoint; протяжка trace-id из `headers`), выбор приёмника и семплирования; пакеты уже в CdcOutbox.Host; не ломать имена и label `slot` существующих метрик prometheus-net.
- **17 — единый стиль комментариев.** XML-doc «что это» по эталону `src/CdcOutbox.Core/Configuration/` на остальной код src (задач 2–8); фиксированная терминология (fencing/checkpoint/standby, без русификаций); магические числа — в именованные константы; дедупликация тест-хелперов.

Ради правила 7 файлов разделены — `LoadProfile`/`BatchResult`/`GeneratedMessage`/`RecoveryDecision`/`OutboxColumnPlan`/`PublicationState`/`ConsumedMessage` в собственных файлах (те же каталоги и namespace, тесты не менялись); enum'ы `BatchOutcome`/`RecoveryAction`/`OutboxColumnSlot` остались при своих классах как допустимые. Проверено 2026-11-06 негативным тестом: до разделения линт падал с SA1402 ровно на 7 файлах; после — зелёный при живых enum+class файлах и class+delegate пробе.
- Спорные предпочтения (var, expression-bodied и пр.) зафиксированы в .editorconfig на уровне suggestion — линт их не блокирует.
- XML-doc комментарии — только в многострочном виде: `/// <summary>`, текст и `/// </summary>` на отдельных строках. Ссылки на файлы документации в коде outbox-сервиса (`CdcOutbox.*`) не используются — ни в runtime-строках, ни в комментариях (решение владельца 2026-11-04; для Writer/KafkaValidator допустимы указатели на контракты — например, AGENTS.md «Тестовое тело»).
- **Содержание комментариев — короткое «что это», без деталей реализации** (решение владельца 2026-11-07): `<summary>` — одна короткая фраза о том, чем является сущность или настройка. Без механики работы, обоснований «почему так», перечислений режимов и источников, ссылок на параметры драйверов (`ProducerConfig LingerMs` и т.п.); единицы измерения (мс/с/байт) — часть смысла и остаются. То же касается inline-комментариев: «что», не «как». Пояснения по реализации и мотивация — в документации (README, корневые .md, справочник этого файла), не в коде. Эталон — `src/CdcOutbox.Core/Configuration/` (вычищен 2026-11-07): «Таймаут доставки сообщения, включая ретраи, мс.», «Название служебного topic checkpoint-стора.». Summary `LeadershipArbiter` приведён к правилу 2026-11-07; остальной код src/ ещё не вычищен.
- **Календарное время — строго через `TimeProvider`** (решение владельца): никаких прямых `DateTime.UtcNow`/`DateTimeOffset.UtcNow` в коде src — каденции, дедлайны, паузы и «возрасты» берутся только у инжектируемого `TimeProvider` (в сервисе — DI-синглтон `TimeProvider.System`), иначе логика времени не проверяется фейковыми часами в тестах. Calendar-сентинелы («никогда» = `DateTimeOffset.MinValue`) запрещены — «никогда» выражается `null`. Измерение коротких интервалов (латентность публикации) — `Stopwatch.GetTimestamp()`: это не календарное время. Тестовый контур может использовать реальные часы.

## Рефакторинги через Rider MCP

JetBrains Rider (MCP) подключён к этому solution — рефакторинги исходного кода доступны как инструменты:

- **Переименование — да**: `rename_refactoring` (контекстно-зависимое, обновляет ВСЕ ссылки на символ по всему solution — не текстовая замена). Переименование public API/типов делать через него, а не replace'ом.
- **Удаление — отдельной рефакторинг-операции нет** (safe delete отсутствует): файлы/символы удаляются обычными средствами (Edit/`git rm`) с обязательной проверкой остаточных ссылок (`search_in_files_by_text`) и прогоном lint+test.
- Сопутствующее: `get_symbol_info` (декларация/семантика символа), `get_file_problems` (инспекции IDE по файлу), `search_in_files_by_text`/`_by_regex`, `reformat_file`, `build_project`. Канонические сборка/линт/тесты — по-прежнему только контейнером через `scripts/*.sh` (локальный SDK не 8.й); инструменты Rider — для навигации, инспекций и рефакторингов, не для замены прогона.

## Ключевые ограничения

- Чтение outbox — только через logical replication slot; SELECT-polling таблицы запрещён.
- Механика CDC — outbox-таблица + pgoutput (pgoutput не передаёт logical messages ни в одной версии PostgreSQL — доставка строится на INSERT).
- Подтверждение LSN слота — только после Kafka delivery (`acks=all`): семантика at-least-once, дубликаты допустимы, потери нет.
- Kafka-клиент всего решения — Confluent.Kafka напрямую: outbox-сервис (идемпотентный продюсер событий `acks=all`, транзакционный продюсер checkpoint'ов `cdc-checkpoints` (fencing лидера) и консюмер control-группы — реализованы задачами 5/10) и консюмер валидатора. KafkaFlow исключён полностью. Из outbox-сервиса — решением владельца 2026-10-22 (нет доступа к Kafka-транзакциям ни в одной линии — [Farfetch/kafkaflow#566](https://github.com/Farfetch/kafkaflow/issues/566) открыт с 2024-04 без реакции мейнтейнеров, проверено рефлексией 3.0.10; полная причина — раздел «Пакеты решения» справочника выше). Из валидатора — решением владельца 2026-10-27: дефект связки KafkaFlow 3.0.10 + Confluent.Kafka 2.3.0 (консюмер назначал партиции и не доставлял ни одной записи; воспроизведено минимальным пробником на чистом KafkaFlow, сырой Confluent с той же конфигурацией работает).
- .NET 8 (`net8.0`) и PostgreSQL 17 — строго; всё в Docker Compose.
- Комментарии в коде (включая XML-doc) — только с разрешения владельца; пояснения по реализации живут в документации (README, корневые .md, раздел «Версии и контракты» этого файла).
