# AGENTS.md

Проект `streaming-outbox`: сервис, читающий outbox-сообщения из PostgreSQL 17 через слот логической репликации (плагин pgoutput, Npgsql Logical Replication API — стриминговая репликация, без polling) и публикующий их в Kafka через Confluent.Kafka.

## Главное правило

**При реализации сервиса опираться на `docs/dependencies.md`, `docs/recommendations.md`, `docs/metrics.md` и `docs/outbox-table.md`.**

`docs/dependencies.md` — единый источник правды о:

- версиях инфраструктуры (PostgreSQL, Patroni, etcd, HAProxy, Kafka, observability-стек);
- версиях NuGet-зависимостей сервиса (Npgsql, Confluent.Kafka, OpenTelemetry);
- формате outbox-таблицы `outbox.messages` (DDL);
- канонических примерах создания publication и failover-слота репликации.

`docs/recommendations.md` — архитектурные требования к реализации CDC-сервиса:

- управление replication slot (создаётся сервисом при первом запуске, идемпотентно) и устойчивые checkpoint'ы;
- конвейер `WAL Read → Kafka Send → Kafka ACK → Durable Checkpoint → LSN Flush` — ни checkpoint, ни LSN не опережают подтверждённую Kafka-доставку;
- at-least-once доставка (дедупликация — Inbox потребителя), backpressure на ограниченных очередях, конфигурируемые пачки/in-flight;
- восстановление после сбоев, монотонность подтверждаемой позиции, явные ошибки вместо тихих пропусков;
- Checkpoint Store — отдельный Kafka topic с log compaction (ключ — имя replication slot), Recovery Mode для ручного аварийного восстановления;
- балансировка экземпляров Active-Passive через Kafka Consumer Group (служебный topic `cdc-checkpoints`): partition группы определяет активного, transactional producer (постоянный `transactional.id` от слота) фенсит устаревших лидеров, эксклюзивность слота — последняя линия защиты;
- контроль простоя потока: при отсутствии новых событий дольше `idle_timeout` сервис пишет WARN в лог, не останавливаясь (drain-режим исключён решением владельца); порядок обновления PostgreSQL (pg_upgrade ≥17 переносит слоты с новыми LSN, dump/restore — нет; перед миграцией — дождаться доставки по idle-предупреждениям, после — согласование checkpoint через `recovery_mode`).

`docs/metrics.md` — обязательные метрики сервиса (prometheus-net, класс `OutboxMetrics`): активность и итерации процессора, отправленные/прочитанные/сохранённые сообщения, ошибки, возраст сообщений (`outbox_message_age_seconds`), латентность публикации, in-flight события, checkpoint-стор (age/lag/ошибки), переподключения к слоту и переключения активного экземпляра; сводная таблица и приоритетные показатели мониторинга.

`docs/outbox-table.md` — описание таблицы `outbox.messages`: назначение (Transactional Outbox), структура полей, партиционирование (`partition` брокера / `outbox_partition` процессора), контракты сервиса (`OutboxMessage`, настройки `OutboxStorageOptions` — схема/таблица; публикация в Kafka — напрямую Confluent.Kafka без интерфейса-транспорта), связь с метриками.

`docs/implementation-plan.md` — план реализации outbox-сервиса из небольших задач с проверяемым результатом (конвейер → устойчивость → режимы → резервирование → приёмка); чек-лист прогресса в начале файла, каждая задача завершается живой проверкой на стенде.

`docs/writer.md` — особенности реализации Writer (запись батча, ретраи и неоднозначный commit, диспетчер, подключения, формат тестового сообщения, метрики): комментарии в коде Writer сознательно минимальны, пояснения по реализации живут здесь.

Любое изменение версии, схемы или архитектурного решения **сначала** фиксируется в этих файлах, **затем** в коде и инфраструктуре.

## Текущее состояние

Из кода реализованы только сервисы тестового контура (перенесены из исследовательского стенда `streaming-polling-outbox` и адаптированы к `outbox.messages`): `src/Writer` (генератор нагрузки, HTTP `:18080`) и `src/KafkaValidator` (валидатор доставки, HTTP `:18083`). Решение — `StreamingOutbox.sln`; сборка/тесты — в контейнере `mcr.microsoft.com/dotnet/sdk:8.0` (156 тестов: 30 Writer + 39 KafkaValidator + 5 Integration-контрактов + 69 CdcOutbox unit + 13 интеграционных; ассерты — Shouldly 4.3.0 во всех тестовых проектах; дефолты конфигурации не содержат значений контура разработки — подключение PG/Kafka и имена слота/publication обязательны через env; полный прогон — `scripts/test.sh`, см. правило ниже). Сам outbox-сервис — задачи 1–3 implementation-plan.md выполнены (каркас + стартовый блок + чтение слота в `OutboxMessage` без публикации; доставка — задачи 4+): `src/CdcOutbox.Host` (хост, Web SDK: `/health` без чеков, `/ready` = postgres-чек (ответ — дефолтный форматтер фреймворка, plain-text статус: чек процессора исключён решением владельца — в Active-Passive standby не держит цикл, но здоров; активность — метрика `outbox_processor_is_active`), `/metrics` prometheus-net; пакеты хостинга — AspNetCore.HealthChecks.Npgsql 9.0.0, OTel 1.11.2/1.11.1, prometheus-net.AspNetCore 5.0.2) и `src/CdcOutbox.Core` (библиотека под всю логику стриминга: Npgsql 9.0.5 + Confluent.Kafka 2.3.0 (librdkafka.redist 2.3.0 — транзитивно, без явного пина) — единственный Kafka-клиент, KafkaFlow исключён — + prometheus-net 5.0.2 + Microsoft.Extensions.Hosting.Abstractions 8.0.1 + Microsoft.Extensions.Options 8.0.2) + `tests/CdcOutbox.UnitTests` и `tests/CdcOutbox.IntegrationTests` (интеграционные — на реальных PostgreSQL/Kafka мини-станда `docker-compose.tests.yml`, compose-проект `streaming-outbox-it`: pg-it postgres:17.2 `wal_level=logical` + kafka-it KRaft один узел, порты наружу не публикуются; фикстура xUnit-коллекции `IntegrationFixture` — env-`IConfiguration` строится один раз, `BuildOptions` через стандартный `AddOptions().Bind().ValidateDataAnnotations()` с in-memory overrides per-test, общие `IAdminClient` и хелперы вызовов БД (`ExecuteAsync`/`QueryAsync<T>`/`GetSlotsAsync`); Testcontainers отклонён; контракт — dependencies.md §2 «Интеграционные тесты»). **Инфраструктура (стенд) перенесена из старого стенда и поднята**: `docker-compose.yml` + `infrastructure/` — Patroni/PostgreSQL 17.2 ×3 (etcd ×3, HAProxy :5432, синхронная репликация, БД `outbox` через bootstrap-with-appdb), Kafka KRaft 3.9.0 ×3 (topic'ы `outbox.events` + `cdc-checkpoints` — checkpoint-стор), Prometheus + postgres-exporter + kafka-exporter, init-db (роли sys_writer/sys_replication/sys_monitor, схема `outbox`, таблица `outbox.messages`, publication `outbox_publication` + гранты sys_replication). Состав минимальный по решению владельца: без PgBouncer, без polling-слоя (sys_app/cdc-функции), без cAdvisor и без харнессов старого проекта. Publication `outbox_publication` создаёт init — 03-outbox-publication.sql (`sys_replication` не может: CREATE PUBLICATION требует CREATE на БД и владения таблицей — экспериментально подтверждено, ремарка в dependencies.md §4); failover-слот `outbox_slot` создаёт сам outbox-сервис при первом старте идемпотентно (задача 2; dependencies.md §5). Полное описание стенда: состав, порты, команды, грабли — **`docs/stand.md`**.

Ключевые правила стенда (подробности и проверки — `docs/stand.md`):

- **Управление стендом — `scripts/stand.sh`**: `up [--build] | down | wipe | bootstrap | status | check | primary | restart | rebuild | logs`, инъекции отказов `fail pg|pgN|pg-all|kafkaN|kafka-all|haproxy|outbox-1|outbox-2|outbox-all` + `restore [target]` (target `outbox-N` стартует `cdc-outbox-N`; outbox-2 — только при включённом профиле `redundancy`, операции с ним идут с флагом `--profile redundancy` — без него compose сервис «не видит»), `switchover [candidate]`, тестовый контур `load <total> [size] [rate]` + `verdict [runId]`. `check` — полный health-check (58 проверок базово — контейнер и /health только cdc-outbox-1, failover-слот outbox_slot создаёт сервис, 9 таргетов Prometheus; с профилем redundancy — 60 и 10, ветки cdc-outbox-2 условные); после смены топологии PG команды сами прогоняют bootstrap и settle-ожидания (первая проба Writer /ready после demote даёт разовую 503 на мёртвом коннекте пула; залипающий postgres-exporter рестартуется автоматически).
- **Полный прогон тестов решения — `scripts/test.sh`**: поднимает/сносит одноразовый мини-стенд интеграционных тестов (`docker-compose.tests.yml`, compose-проект `streaming-outbox-it` — отдельный от основного стенда, host-портов нет) и исполняет `dotnet test StreamingOutbox.sln` в контейнере sdk:8.0 в сети стенда (сам передаёт env `CDCOUTBOX__POSTGRES__CONNECTIONSTRING`/`CDCOUTBOX__KAFKA__BOOTSTRAPSERVERS` — те же имена, что у сервиса). Интеграционные тесты без стенда не исполняются — skip-логики нет (падают Required-валидацией конфигурации/подключением); быстрые unit-прогоны — `dotnet test tests/<проект>` в sdk-контейнере; `wipe.sh` сносит и мини-стенд.
- **Никогда не запускать `docker compose up`/`run` без `--no-deps` на живом стенде** — compose пересоздаст pg-контейнеры (флап промоушенов Patroni). Один сервис: `stand.sh rebuild X` (build + `up -d --no-deps X`); полный сброс — `stand.sh wipe`.
- **После пересоздания pg-контейнеров — `docker compose restart haproxy`** (резолвит имена нод один раз при старте).
- **После каждой смены primary — `scripts/init/apply-bootstrap.sh`** (обновляет `synchronized_standby_slots` на новом лидере).
- Host-порты совпадают со старым стендом `streaming-polling-outbox` (5432, 8008-8010, 8404, 9090, 9092-9094, 18080, 18083) плюс новые 18084/18085 (cdc-outbox-1/2) — оба стенда одновременно не поднять; docker-подсеть новая (10.98.0.0/16).
- `docker compose kill` контейнера НЕ перезапускает его (рестарт-политика не применяется) — возврат явным `docker compose start`.

- **Проекты `src/Writer` и `src/KafkaValidator` — НЕ reference и НЕ образец того, как писать код outbox-сервиса** (решение владельца): это сервисы тестового контура, перенесённые из старого исследовательского стенда, — их стиль и архитектурные паттерны НЕ распространяются на outbox-сервис, код нового сервиса пишется с нуля без оглядки на их структуру. Как писать код, определяют `docs/*.md` (главное правило выше) и правила `.editorconfig`/линта, а не эти проекты.
- **Writer и KafkaValidator — самостоятельные проекты: общего кода с outbox-сервисом и между собой НЕ имеют.** Контракт тестового body/key зафиксирован в `docs/outbox-table.md` и сознательно продублирован в коде обоих сервисов.
- Writer: INSERT+DELETE одной транзакцией (таблица всегда пустая); id — `bigint` identity, резервируется `nextval` ДО сборки body и вставляется с `OVERRIDING SYSTEM VALUE` (детали и гранты sys_writer — `docs/dependencies.md` §3, «Запись тестовой нагрузки»); повтор батча теми же id → `unique_violation` = детект AlreadyCommitted.
- KafkaValidator: идентичность сообщения — `body.id` (= id строки, `long`), группировка — `body.runId`; консюмер KafkaFlow 3.0.10 (группа `kafka-validator`, Earliest, `WithoutStoringOffsets` — рестарт всегда перематывает topic с начала); обогащение снапшотом CDC удалено до появления outbox-сервиса (`verdict.Cdc` всегда null).
- Метрики обоих сервисов — prometheus-net 5.0 (`Metrics.Create*`, `MapMetrics`), без OTel; OTel-пины 1.11 — для outbox-сервиса. Грабли: внутри namespace `*.Metrics` имя `Metrics` резолвится в namespace — квалифицировать `Prometheus.Metrics`; `UseMetrics` в 5.0 нет — достаточно `MapMetrics`; labels — `WithLabels(...).Inc(...)`.

## Линт (обязательно)

- Код и тесты проверяются на соответствие `.editorconfig` (корень репозитория): **после любого изменения `.cs`/`.csproj` запускать `scripts/lint.sh`** (обёртка над `dotnet format StreamingOutbox.sln --verify-no-changes` в контейнере `mcr.microsoft.com/dotnet/sdk:8.0`). Линт должен быть зелёным так же, как сборка и тесты, — до завершения работы. Авто-фикс нарушений: `dotnet format StreamingOutbox.sln` без `--verify-no-changes` (правки пересматривать по диффу).
- **Строгая сборка — `Directory.Build.props`** (применяется ко всем проектам): `TreatWarningsAsErrors`, `EnableNETAnalyzers` + `AnalysisLevel=preview`, `EnforceCodeStyleInBuild` — правила .editorconfig уровня warning/error блокируют и сборку (проверено на SDK 8.0: CS0219-warning валит сборку; IDE0161 из .editorconfig валит сборку). **IDE0005 (неиспользуемые using'и) блокирует и сборку, и dotnet format** (проверено 2026-10-22 негативным тестом; раньше молча пропускался из-за опечатки в ключе .editorconfig — `dotnet_diagnostic.IDE0005_severity` с подчёркиванием вместо точки игнорируется целиком).
- Блокирующие правила (severity warning/error в .editorconfig): форматирование (4 пробела, LF, UTF-8, финальный перевод строки, без хвостовых пробелов), file-scoped namespaces, using вне namespace + System-группой первой, без `this.`, явные модификаторы доступа, скобки у многострочных `if` (`when_multiline`), нейминг (типы/методы/свойства PascalCase, интерфейсы `IPascalCase`, private instance-поля `_camelCase`, `const`/`static` — PascalCase, параметры/локальные camelCase), readonly-поля, где возможно, авто-свойства, target-typed `new()`, неиспользуемые using'и (IDE0005 — для его корректной работы в csproj включён `GenerateDocumentationFile` + `NoWarn CS1591`).
- Спорные предпочтения (var, expression-bodied и пр.) зафиксированы в .editorconfig на уровне suggestion — линт их не блокирует.
- XML-doc комментарии — только в многострочном виде: `/// <summary>`, текст и `/// </summary>` на отдельных строках.

## Ключевые ограничения

- Чтение outbox — только через logical replication slot; SELECT-polling таблицы запрещён.
- Механика CDC — outbox-таблица + pgoutput (pgoutput не передаёт logical messages ни в одной версии PostgreSQL — доставка строится на INSERT).
- Подтверждение LSN слота — только после Kafka delivery (`acks=all`): семантика at-least-once, дубликаты допустимы, потери нет.
- Kafka-клиент outbox-сервиса — Confluent.Kafka напрямую: идемпотентный продюсер событий (`acks=all`), транзакционный продюсер checkpoint'ов `cdc-checkpoints` (фенсинг лидера), консюмер control-группы. KafkaFlow в outbox-сервисе исключён (решение владельца 2026-10-22): нет доступа к Kafka-транзакциям ни в одной линии — [Farfetch/kafkaflow#566](https://github.com/Farfetch/kafkaflow/issues/566) открыт с 2024-04 без реакции мейнтейнеров, проверено рефлексией 3.0.10 (публичный API без транзакционных членов, обёрнутый IProducer наружу не торчит); полная причина — `docs/dependencies.md` §2. KafkaFlow 3.0.10 остаётся только в KafkaValidator (тестовый контур).
- .NET 8 (`net8.0`) и PostgreSQL 17 — строго; всё в Docker Compose.
- Комментарии в коде (включая XML-doc) — только с разрешения владельца; пояснения по реализации живут в `docs/*.md` (стиль Writer — `docs/writer.md`).
